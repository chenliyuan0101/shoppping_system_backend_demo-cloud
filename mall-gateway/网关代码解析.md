# `mall-gateway` 代码解析

> 范围：`backend/mall-cloud/mall-gateway/src/main/java/com/mall/gateway`（**8 个类 / 1019 行**）+ 它依赖的 `resources/application*.yaml` 配置。
> 目的：讲清"请求进来以后，谁在什么顺序上做了什么决定"，以及每个类的**对外契约**与**容易写错的点**。
> 系统全貌见 `系统说明.md`；流程与三大功能见 `系统流程与三大核心功能实现.md`；这里的"为什么这么写"多数在类注释里有原始记录。
> **本文所有结论都对着代码核过**（含行号位置），下面提到的"坑"都能在对应类注释或测试里找到出处。

**没有 `@Configuration` 类**：5 个过滤器都是 `@Component` + `implements GlobalFilter, Ordered`，
`@SpringBootApplication` 扫 `com.mall.gateway.**` 自动装配；顺序由各自的 `getOrder()` 决定。
**网关不带 Lombok**（日志用原生 `LoggerFactory.getLogger(...)`，与 mall-trade/其余服务口径一致）。
**网关不依赖 `mall-common`**（v5.2 的共享内核里没有它）：所以错误响应体是**手写字符串**——
改文案时不能靠 IDE 重命名，只能逐字比对。

## 1. 请求处理链（顺序即语义）

```
客户端
 └─ ① InternalPathBlockFilter        HIGHEST       路径以 /internal/ 开头 ⇒ 404（空 body），不进路由
     └─ ② TraceIdFilter              HIGHEST+1     定/复用 traceId（形状闸门）→ 覆盖头 → 日志 → 转发
         └─ ③ MemberIdentityFilter   HIGHEST+5     剥离伪造会员头 → 验签 → typ=user → 令牌版本 → 注入会员三件套
             └─ ④ AdminIdentityFilter HIGHEST+6   剥离伪造 X-Admin-*/X-Gateway-Auth(仅 /api/admin) →
                                                   /api/admin/** 且非登录路径 → 验签 → typ=admin →
                                                   状态缓存(403) → 令牌版本(401) → 注入管理端三件套
                 └─ ⑤ GatewayRateLimitFilter HIGHEST+10  Redis 计数 → 超限 429（HTTP 200）
                     └─ ⑥ 路由（9 条，按声明顺序）→ lb://mall-xxx（Nacos + LoadBalancer）
```

**顺序不是审美，是三处硬约束**（都是踩过的）：

| 约束 | 为什么 |
|---|---|
| ① 必须在最前 | 若先路由再判断，`/internal/**` 会先被转发出去（P1 的路由是 `Path=/**`，等于把"能扣库存/核销券"的接口挂到外网） |
| ② 必须紧跟 ① | 被 ① 拦掉的请求**也要有 traceId**（拦截原因同样需要能被串起来） |
| ④ 必须在 ③ 之后 | ③ 会**无条件剥离** `X-Gateway-Auth`；④ 若排在它前面，注入的凭据随后会被删掉 ⇒ 下游拿到"没有凭据的 `X-Admin-Id`" ⇒ 管理端全线未登录 |
| ④ 必须在 ⑤ 之前 | 限流应当在**身份确定之后**计数（会员侧同理：③ 也在 ⑤ 之前） |

## 2. 逐类解析

### 2.1 `MallGatewayApplication`（22 行）

唯一的启动类，`@SpringBootApplication` 扫 `com.mall.gateway.**`。类注释保留了历史：
P1 只做"收流量 + 按路径转发"，后面的 JWT 预校验、限流、按路径切换服务都是逐批加的。
**职责上的意义**：网关是"回退 = 改路由，秒级生效"这个能力的载体，所有灰度都从它切。

### 2.2 `config/InternalPathBlockFilter`（46 行，order = HIGHEST）

```java
if (path.startsWith("/internal/")) {                       // INTERNAL_PREFIX = "/internal/"
    exchange.getResponse().setStatusCode(HttpStatus.NOT_FOUND);
    return exchange.getResponse().setComplete();           // 空 body
}
return chain.filter(exchange);
```

- **为什么返回 404 而不是 403**（注释原文的理由）：403 等于告诉探测者"路径存在但你没权限"，404 连存在性都不确认。
- **为什么响应体是空的**：网关不依赖 `mall-common`，不该为了"凑统一格式"把下游的响应体约定搬上来。
- **两道防线**：网关挡外网路径；`X-Internal-Token`（各服务的 `InternalApiAuthInterceptor`）挡"能直连服务端口"的情况。
- ⚠️ **不要"顺手修"成 403 或加上 `{code,message,data}`**：会同时破坏"不暴露存在性"和"网关不依赖共享内核"。

### 2.3 `support/TraceIdFilter`（83 行，order = HIGHEST+1）

```java
String incoming = request.getHeaders().getFirst(TRACE_ID_HEADER);   // "X-Trace-Id"
String traceId = (incoming != null && SAFE.matcher(incoming).matches()) ? incoming : newTraceId();
// SAFE = ^[A-Za-z0-9_-]{8,64}$
ServerHttpRequest mutated = request.mutate().headers(h -> h.set(TRACE_ID_HEADER, traceId)).build();
log.info("trace={} 入口 {} {} 来源={}", traceId, method, rawPath, reused ? "复用客户端" : "网关生成");
```

三条刻意写进注释的口径：

1. **客户端值只在"形状可信"时复用**：`[A-Za-z0-9_-]{8,64}`。不匹配（空/超长/含空格换行）⇒ 丢弃并重新生成。
   理由：traceId 不是凭据，复用它对排障有价值（前端/压测可自带 id 串链路），但它**会进日志** ⇒ 必须先过形状闸门防**日志注入**。
2. **无论复用还是生成，都"覆盖"再转发**（`h.set`）：下游只会看到一个网关认可的值，不会出现双值歧义。
3. **网关自己不打 MDC**：Reactor 线程会在池间跳，ThreadLocal 不可靠 ⇒ 网关用**显式打日志**；下游（Servlet 栈）才用 MDC。
   这就是为什么下游服务能看到 `[traceId]` 前缀、而网关的日志里是 `trace=...` 这种显式形式。

新 id = UUID 去掉 `-` 取前 16 位（够唯一、又不刷屏）。

### 2.4 `auth/MemberIdentityFilter`（189 行，order = HIGHEST+5）

**改造前后**（类注释）：以前每个带 `@MemberId` 的请求都由各服务自己"验签 → 查 `ums_member` → 读 Redis 令牌版本"，
20+ 端点、6 个域，且用户中心一挂全站 401；现在网关验一次，把身份注入头往下传：

```
X-Gateway-Auth: <共享密钥>      ← 下游据此判断"这个身份是网关给的，不是客户端伪造的"
X-Member-Id:    <memberId>
X-Member-Ver:   <tokenVersion>
```

**执行顺序**（代码里就是这五步）：

1. **无条件剥离**客户端自带的 `X-Gateway-Auth`/`X-Member-Id`/`X-Member-Ver`（注释原话："这是本过滤器最容易写错、后果最严重的一行"——
   不剥的话，任何人手写 `X-Member-Id: 1` 就变成了别人）。
2. 开关关闭或共享凭据未配置 ⇒ 只转发剥离后的请求（**不验签、不注入**，下游回落到自行验签）。
3. 没有 `Authorization: Bearer xxx` ⇒ **放行**（匿名请求；是否要求登录由下游按方法签名决定，例如 `@MemberId` 会 401）。
4. 验签/有效期失败 ⇒ `401 登录已失效，请重新登录`。
5. `typ != user` ⇒ **原样透传**（管理端令牌归 `AdminIdentityFilter` 管）；
   `typ == user` ⇒ 比对 `mall:token:ver:user:{id}`，不等 ⇒ 401；相等 ⇒ 注入三件套后转发。

**令牌版本比对（`versionMatches`）的三条细节**：

```java
String key = "mall:token:ver:user:" + claims.userId();
... get(key)
   .map(v -> v == null || v.isBlank() ? claims.ver() == 0L        // 键不存在 = 版本 0（与单体 current() 语义一致）
              : (Long.parseLong(v.trim()) == claims.ver()))        // 值非数字 ⇒ true（"不可判定"不误伤）
   .defaultIfEmpty(claims.ver() == 0L)
   .onErrorResume(e -> true);                                      // Redis 故障 ⇒ fail-open
```

> ⚠️ 这里和 5.3 节讲的 `CacheService` 有个**容易混淆的分工**：网关只读**令牌版本**键；
> `mall:cache:member:status:{id}` 是各服务的 `MemberSession` 在读写（网关不读它）。

**失败响应形态**：`HTTP 200` + `{"code":401,"message":"登录已失效，请重新登录","data":null}`（手写字符串，逐字契约）。

### 2.5 `auth/AdminIdentityFilter`（358 行，order = HIGHEST+6）

管理端与会员侧**同构**（同一种形状、同一份文案、同一种 fail-open），但多了两条管理端独有的逻辑。

**① 三条/四条文案都是"本过滤器"产出**（逐字照抄改造前的单体，C1 判据）：

| 触发条件 | code | message |
|---|---|---|
| 缺 `Authorization` / 不是 `Bearer xxx` | 401 | `未登录` |
| 验签失败 / 过期 / 令牌版本不符 | 401 | `登录已失效，请重新登录` |
| `typ != admin`（含会员令牌、大小写不同的 `ADMIN`） | 401 | `登录已失效，请使用管理员账号登录` |
| 状态缓存说"已禁用" | **403** | `账号已被禁用` |

**② 剥离规则与会员侧不同（这是最容易写错的地方）**：

```java
// X-Admin-* : 任何路径都剥 —— 除了本过滤器，没有任何合法来源会写这些头
// X-Gateway-Auth : **只在 /api/admin 路径**剥 —— 会员路径上的那个头是会员过滤器刚注入的，剥掉就是 P3 回归
ServerHttpRequest stripped = stripForgeable(request, adminScoped);
```

- ⚠️ **Spring Framework 7 的 `HttpHeaders` 不再是 `Map`**：取头名要用 `headerNames()`（注释里明确记了这条，`keySet()` 不行）。
- ⚠️ **判定顺序刻意是"先状态(403)、后版本(401)"**，与单体 `AdminSession.resolve` 一致：
  否则"已禁用 + 版本已 bump"的管理员会拿到 401 而不是 403（**文案漂移**，C1 会红）。

**③ 状态缓存 `mall:cache:admin:status:{id}`**：网关**读缓存、不查库**（网关没有也不该有 datasource）。
取值支持两种写法——JSON（`{"adminId":9,"username":"admin","status":0}`，与会员侧 `MemberStatusVO` 同构）
或裸数字（`"0"`/`"1"`）；判据是"可解析且 `!= 1` ⇒ 禁用 ⇒ 403"。
**键缺失 / 值不可解析 / Redis 不可用 ⇒ fail-open 放行**（交给令牌版本与下游兜底）。

**④ 只介入 `/api/admin/**`**：

```java
static boolean isAdminScoped(String path) {   // 与单体 addPathPatterns("/api/admin/**") 同义
    if (!path.startsWith("/api/admin")) return false;
    return path.length() == "/api/admin".length() || path.charAt("/api/admin".length()) == '/';
}
```
⇒ `/api/admin`、`/api/admin/**` 在内；`/api/administrator/**` **不在内**（不是同一段）。
唯一放行的是 `/api/admin/auth/login`（与单体 `excludePathPatterns` 逐字对应）——**放行路径上仍然剥离伪造头**。
会员路径上，本过滤器**完全不介入**：不拒绝、不注入，**连 Redis 都不读**（有专门测试钉住）。

**⑤ 两个独立回退开关**：`mall.gateway.admin-auth.enabled=false`（管理端）与 `mall.gateway.auth.enabled=false`（会员侧）**互不影响**——
会员侧一键回退不会**静默**把管理端验签一起关掉（管理端是"人的入口"，回退必须显式）。

### 2.6 `config/GatewayRateLimitFilter`（180 行，order = HIGHEST+10）

**与各服务内部限流的分工**（注释）：各服务的 `RateLimitAspect` 管"按接口维度"（上传 20/分、注册 10/分…）；
本过滤器是**另一层**：按调用方整体的粗粒度总量控制，挡在入口。两级阈值不同、用途不同，都保留。

**四个刻意的细节**：

1. **Key**：`mall:rl:gw:{identity}` —— 与各服务 `mall:rl:{scope}:{identity}` 同前缀、不同 scope（计数互不干扰）。
2. **超限返回 HTTP 200 + `code=429`**（文案 `操作过于频繁，请稍后再试`，与单体逐字一致）：
   因为对外契约是"HTTP 恒 200、结果看 code"。若返回 HTTP 429，前端 axios 会当成网络错误、拿不到提示——
   所以**不能**直接用网关自带的 `RequestRateLimiter`（它固定回 HTTP 429）。
3. **身份维度默认取传输层来源地址**，**不信任** `X-Forwarded-For`/`X-Real-IP`（客户端可伪造，采信等于把限流开关交给攻击者：
   换个假 IP 就是全新计数桶）。只有显式打开 `trust-forwarded-for` 才知道去读 XFF 的第一个地址。
4. **Redis 不可用 ⇒ fail-open 放行**：限流是保护措施，不是业务规则。

**🔴 这个类里修过的一个真缺陷（P7 收口演练发现，值钱）**：
早先的写法把 `onErrorResume(...)` 挂在**整条链**上（`increment().flatMap(放行/限流).onErrorResume(chain.filter)`），
于是 `chain.filter(exchange)` 里**任何下游故障**（例如 `lb://mall-admin` 实例不可达）都会被当成"限流计数失败"吞掉，
并**第二次**调用 `chain.filter`。现象：下游已停，客户端却拿到 **HTTP 200 + 空 body**（既不是契约体三字段，也不是 503），
日志里还有一条误导性的"限流计数失败"。
修法：**fail-open 的作用范围严格止步于那一次 Redis 递增**——现在异常处理只写在 `increment(key)` 与 `ensureWindowTtl(...)` 里，
其余异常一律向上抛。回归闸门：`GatewayRateLimitFilterTest#downstreamFailureMustNotBeSwallowed`。

### 2.7 `auth/GatewayJwtUtil`（126 行）

极简 HS256 JWT 的**网关侧副本**（与签发方同算法、同 claims）。三点值得注意：

1. **为什么复制而不是抽公共 jar**（注释）：验签这种"必须与签发方逐字节一致"的东西，
   抽成共享库会把"网关能不能升级"和"用户中心能不能升级"重新绑死——契约靠**逐字相同 + 契约测试**守，不靠同一个 class 文件。
2. **构造时就 fail-fast**：`mall.jwt.secret` 缺失 ⇒ `IllegalStateException`；短于 32 位 ⇒ 也拒绝启动。
   注释原话：否则最容易发生的事故是"网关用空密钥验签，把所有请求判成未登录"，或者反过来漏验。
3. **解析只做"签名 + 有效期 + sub/exp 必需"**，**不校验 `typ`/`ver`**（那是调用方即过滤器的职责）；
   `ver` 缺失按 0 处理；`claims` 的字段名/顺序与单体一致（`sub`/`name`/`typ`/`ver`/`iat`/`exp`）。
   签名比对用 `MessageDigest.isEqual`（常量时间，避免签名比对侧的时序侧信道）。

### 2.8 `auth/InvalidTokenException`（15 行）

只有一句话的运行时异常。**刻意不复用单体的 `BusinessException`**：网关是独立进程，
引入单体的异常体系等于让网关依赖一个它不需要的模块；过滤器只需要知道"验证没过"，对外的文案由过滤器统一决定。

## 3. 三张"契约表"（改任何一处都要同步）

### 3.1 注入头（谁写 → 谁读）

| 头 | 写方 | 读方 | 说明 |
|---|---|---|---|
| `X-Gateway-Auth` | 网关（会员/管理端**同一把** `mall.gateway.auth-token`） | 各服务的 `MemberSession` / `AdminIdentityResolver` | 常量时间比较；不通过就不信任何身份头 |
| `X-Member-Id` / `X-Member-Ver` | 网关 `MemberIdentityFilter` | 各服务 `@MemberId` 解析器 / `MemberSession` | 客户端伪造的会被**无条件剥离** |
| `X-Admin-Id` / `X-Admin-Ver` | 网关 `AdminIdentityFilter` | `mall-admin` 的 `AdminIdentityResolver`、`mall-product` 的 `AdminIdentityResolver` | `X-Admin-*` 在**任何路径**都被剥离 |
| `X-Trace-Id` | 网关 `TraceIdFilter`（或复用客户端合规值） | 各服务的 `TraceIdFilter` → MDC → 出站 `OutboundHeadersInterceptor` | 客户端无 `X-Gateway-Auth` 时下游回落自行验签 |

### 3.2 Redis key（谁写 → 谁读）

| key | 写方 | 读方 | 语义 |
|---|---|---|---|
| `mall:token:ver:user:{id}` | `mall-user-center`（登出/改密/禁用时 `INCR`） | **网关**（会员路径） | 不等 ⇒ 401；键不存在 ⇒ 版本 0 |
| `mall:token:ver:admin:{id}` | `mall-admin`（登出/禁用/对账补写时 `INCR`） | **网关**（管理端路径） | 同上 |
| `mall:cache:admin:status:{id}` | `mall-admin`（禁用时**写** 0，对账补写） | **网关**（管理端路径，产出 403） | 可解析且 `!=1` ⇒ 403；缺失/不可解析 ⇒ fail-open |
| `mall:cache:member:status:{id}` | `mall-user-center`（改状态时**只删不写**） | **各服务的 `MemberSession`**（网关**不读**） | 读不到就回源 `/internal/v1/user/member/{id}/snapshot` 并回填 |
| `mall:rl:gw:{ip}` | 网关限流 | 网关限流 | 固定窗口计数，首次计数时写 TTL |

### 3.3 响应文案（HTTP 恒 200 + `{code,message,data}`）

| 场景 | code | message | 出处 |
|---|---|---|---|
| `/internal/**` 被挡 | —（**HTTP 404 + 空 body**） | — | `InternalPathBlockFilter`（刻意不套契约体） |
| 会员令牌失效/过期/版本不符 | 401 | `登录已失效，请重新登录` | `MemberIdentityFilter` |
| 管理端缺令牌/格式错 | 401 | `未登录` | `AdminIdentityFilter` |
| 管理端令牌失效/过期/版本不符 | 401 | `登录已失效，请重新登录` | `AdminIdentityFilter` |
| 会员令牌打后台 | 401 | `登录已失效，请使用管理员账号登录` | `AdminIdentityFilter` |
| 管理员被禁用 | 403 | `账号已被禁用` | `AdminIdentityFilter`（读状态缓存） |
| 触发网关限流 | 429 | `操作过于频繁，请稍后再试` | `GatewayRateLimitFilter` |

> 上表 6 条 `code/message` 都在 `p6-c1-baseline.ps1` 的 42 项逐字比对范围内（`/api/auth/**`、`/api/admin/auth/**` 等）。

## 4. fail-open / fail-closed 策略矩阵（网关最容易写错的地方）

| 判据 | 失败/缺失时的行为 | 为什么 |
|---|---|---|
| `mall.jwt.secret` 缺失或 < 32 位 | **启动失败**（fail-closed） | 空密钥验签 = 把所有请求判成未登录，或反过来漏验 |
| `mall.gateway.auth-token` 未配置 | **不注入身份**（少给，不给错的） | 不给下游一个它无法验证的身份；下游回落自行验签 |
| Redis 读**令牌版本**失败 | **放行**（fail-open） | 缓存故障不该把全体用户/管理员踢下线（与单体 `TokenVersionService.matches` 同口径） |
| Redis 读**管理端状态缓存**失败 / 键不存在 / 值不可解析 | **放行**（fail-open） | 缓存是加速层，不是唯一判据；"立即失效"由令牌版本保证；且本过滤器必须**纯增量** |
| Redis **限流计数**失败 / TTL 写失败 | **放行**（fail-open） | 限流是保护措施，不该成为全站单点 |
| **下游服务的故障** | **原样抛出**（不许吞） | 曾把下游故障吞成"HTTP 200 + 空 body"，见 2.6 的缺陷 |
| `typ` 不是 `user`（会员侧） | **透传**（交给管理端过滤器） | 会员侧若"看到非 user 就拒绝"，管理端会当场全挂 |
| `typ` 不是 `admin`（管理端侧） | **401**（fail-closed） | 双体系隔离：会员令牌不得用于后台接口 |

## 7. 改这个包时的须知（按"会怎么坏"排序）

1. **别改 filter 顺序**：改 `getOrder()` 之前先读 §1 的三条硬约束，尤其"④ 必须在 ③ 之后"。
2. **剥离步骤不能省、不能缩范围**：`X-Admin-*` 任何路径都剥；`X-Gateway-Auth` 只在 `/api/admin` 剥（会员路径上剥掉 = P3 回退）。
3. **文案逐字**：6 条 `code/message` 是 C1 判据；改完必须跑 `p6-c1-baseline.ps1 -Mode compare`（42 项）。
4. **永远是 HTTP 200**：除了 `/internal/**` 的 404（刻意）与限流的 `code=429`，业务失败都要 200 + code。
5. **fail-open 的边界**：只允许"Redis 读/写失败"放行；**下游异常必须抛出**（否则会重现"空 200"缺陷）。
6. **网关不查库、不依赖 `mall-common`**：需要新数据就加缓存键（由属主服务写），不要引 datasource。
7. **`HttpHeaders` 不是 Map**（Spring 7）：遍历头名用 `headerNames()`。
8. **新增放行路径要谨慎**：现在只有 `/api/admin/auth/login` 一条；放行意味着"不验签"，但**仍然剥离伪造头**。
9. **改动后最小验证集**：网关 55 例 + `p6-c1-baseline.ps1` + 一次经网关的冒烟（`/api/home/index`、`/api/product/1001`、管理员登录 + 看板）+
   traceId 四边贯通（见 §8）。
