# `mall-content` 代码解析

> 一句话定位：商城**内容域**服务（8107 / `mall_content`）——独家持有 `cms_banner`、`cms_notice` 两张表与 MinIO 图片存储；对外只提供**首页聚合 + 前台读**（3 个匿名端点），对**写**只开放 `/internal/v1/content/**`（`X-Internal-Token`）。
> 范围：`backend/mall-cloud/mall-content/src/main/java` 下 **43 个文件 / 2134 行**（`Get-ChildItem -Recurse -Filter *.java` + `Get-Content` 物理行数，含空行）；测试 **6 个测试类 + 1 个基类 / 28 例**（取 `target/surefire-reports/*.txt` 的 `Tests run` 聚合，见 §10）。
> 与其它文档的分工：本文讲"代码怎么组织、怎么实现"；端口/路由/数据属主见 `系统说明.md`，一次请求的生命周期与三大功能见 `系统流程与三大核心功能实现.md`。**本文结论均对着代码核过并附行号**；推测一律显式标注「（推测：…）」。

## 2. 分层与包职责

| 包 | 放什么 | 不放什么 / 架构规则 |
|---|---|---|
| `controller` | 只有对外公开读的 `*Controller` | 不放业务逻辑、不放鉴权（本层无登录态可鉴）。守：`CodeStyleTest#controllerNaming` |
| `internal` | `/internal/v1/content/**` 入站控制器 | 鉴权写在拦截器里而不是控制器里 `if`；受 `domain/support` 反依赖规则约束 |
| `service` / `service.impl` | 接口 + 实现；本服务**全部**业务逻辑（聚合、降级、缓存失效、字段校验） | 不放 HTTP 形状（`MultipartFile` 是唯一例外，落在 `FileStorageService`）。守：`#serviceNaming` |
| `domain` | MyBatis-Plus 实体，字段与列一一对应 | 不得依赖入站/服务/客户端层。守：`#domainDoesNotDependOnOuterLayers` |
| `mapper` | 只 `extends BaseMapper<T>`，不写 SQL/XML | 守：`#mapperNaming` |
| `dto` / `support.dto` | 入参 `*SaveRequest`、出参 `*VO`、聚合体 `HomeData`、跨服务契约快照 | 不放实体。守：`#dtoNaming`（后缀白名单含 `VO`/`Request`/`Data`/`Node`） |
| `client` | 出站 `*Api` + `*Client` + `*Exception` | 不写降级（降级是 service 的策略）。守：`#clientNaming` |
| `config` | **组装根**：`@Configuration`、`HandlerInterceptor`、`@ConfigurationProperties` 装配 | 不放业务。守：`#configNaming` |
| `support` | 无业务语义的工具/常量/契约副本、响应体与异常、MinIO 装配 | 不得依赖入站/服务/客户端层。守：`#supportDoesNotDependOnOuterLayers` |
| `upload` | 存储实现（MinIO 写入 + 魔数识别） | 不放业务判断（"要不要存"在控制器，"怎么存"在这里） |

**组装根 = `config/` 包（不是 `app/`）**：`ContentApplication` 只做 `SpringApplication.run`（`ContentApplication:17-22`），装配全落在 `config/`（`WebConfig` 注册拦截器、`MybatisPlusConfig` 扫 mapper、`LoadBalancedClientConfig` 提供 `@LoadBalanced` builder、`MinioConfig` 提供 `MinioClient`、`OpenApiConfig` 补文档示例）。`ContentApplication:9-15` 明说本工程是"后续 6 个服务的模板"，模板要素 = 自带组装根 + 自带共享内核副本 + 自带数据源。
**本模块唯一的架构闸门是 `CodeStyleTest`（10 条 ArchUnit 规则）**；带 B 编号的 `ModuleBoundaryTest`（B5 组装根 / B6 共享内核）是单体与 mall-trade 那侧的闸门，本服务没有这个类（`src/test` 下只有 §10 列的 7 个文件）。

## 3. 核心类详解

### 3.1 `HomeController`（39 行）

对外的三个**匿名只读**端点，直接转发给 `HomeService`，自己不做加工（`HomeController:26-27,31-32,36-37`）。类注释标明来源《接口文档.md》2.2（`:16`）⇒ 形状是既有对外契约的一部分。测试：`PublicContentReadMySqlTest`、`HomeAggregationMySqlTest`。

### 3.2 `InternalBannerController`（69 行）/ `InternalNoticeController`（60 行）

轮播/公告的后台写入口，形状与 `/api/admin/banner/**`、`/api/admin/notice/**` **逐字同构**（差别只有 URL 前缀与鉴权方式）。

- 分页参数默认值：`pageNum=1`、`pageSize=10`（`InternalBannerController:42-43`），钳制在 service。
- **响应直接返回实体 `Banner`/`Notice`**（`:44`）：`InternalBannerController:28-30` 说明这是**故意的**——它就是 `/api/admin/banner/page` 现在的 JSON 形状，C1 要求逐字不变；P8 再统一换成显式 DTO + 契约测试。
- 启停走独立端点并收 `{"status": …}` 小对象（`StatusRequest`，`:58-62`），不是查询参数——`mall-trade` 的 `ContentInternalApi:61-63` 也按这个小对象发。
- 契约由 `InternalContentApiMySqlTest#adminPageFieldsUnchanged`（4 个分页字段 + 8 个实体字段名）与 `#errorMessagesUnchanged` 钉住（`:136-181`）。

### 3.3 `InternalUploadController`（72 行）

**唯一决定"哪些字节允许进公开桶"的地方**——校验顺序是 大小 → 真实类型（魔数）→ 落库（`:45-49`）：

```java
if (file == null || file.isEmpty())       throw new BusinessException(400, "请选择文件");                        // :51-53
if (file.getSize() > maxMb * 1024 * 1024) throw new BusinessException(400, "图片不能超过 " + maxMb + "MB");      // :54-56
try (InputStream in = file.getInputStream()) { type = ImageTypeDetector.detect(in); }                          // :57-62
if (type == null) throw new BusinessException(400, "仅支持 jpg/png/webp/gif 图片（按文件内容识别，请勿修改后缀）"); // :63-65
return fileStorageService.upload(file, type);                                                                  // :66
```

| 场景 | code | message（逐字） |
|---|---|---|
| 空文件 | 400 | `请选择文件` |
| 超过 `mall.upload.image-max-mb`（默认 5）MB | 400 | `图片不能超过 5MB`（数字随配置） |
| 读流失败 | 400 | `文件读取失败`（`:61`） |
| 魔数识别不出 | 400 | `仅支持 jpg/png/webp/gif 图片（按文件内容识别，请勿修改后缀）` |
| 成功 | 0 | `data = {url, name, size, contentType}`（`:69-71`） |
| MinIO 写入失败 | 500 | `上传失败，请确认 MinIO 已启动`（`FileStorageService:59`） |

**multipart 报文形状**（两侧合起来看）：本服务侧 `@RequestParam("file") MultipartFile file`（`:41`）⇒ part 名固定 **`file`**；调用方 `mall-trade/common/client/ContentInternalClient.java:130-147` 用 `MultiValueMap` + `add("file", new ByteArrayResource(bytes){ getFilename(){…原始名或"file"; }})`，由 `ContentInternalApi:103` 的**方法级** `contentType="multipart/form-data"` 交给 `FormHttpMessageConverter` 生成边界与 part 头（`:91-104` 解释了为什么不会退化成"把 map 当 JSON 发"）。上限是两套口径：容器 `spring.servlet.multipart.max-file-size: 10MB` / `max-request-size: 15MB`（`application.yaml:16-19`），业务 `mall.upload.image-max-mb`（默认 5，`InternalUploadController:37-38`）——>10MB 由容器先拒，走不到本服务的 400 文案。测试：`InternalUploadMySqlTest`（4 例）。

### 3.4 `HomeServiceImpl`（124 行）★ 本文主角

首页聚合：Banner/公告来自本库，类目/热门/新品来自**商品域一次跨进程调用**，整体走 Redis 整页缓存。四个常量/字段：`SECTION_SIZE = 8`（`:47`）、`HOME_TTL = 45s`（`:50`）、`HOME_DEGRADED_TTL = 5s`（`:53`）、依赖 4 个 bean（`:55-58`）。

```java
HomeData cached = cacheService.getJson(CacheKeys.homeIndex(), HomeData.class);
if (cached != null) return cached;                        // :62-65  命中即返回，不再判断商品域可用性
HomeFeedVO feed = null; Duration ttl = HOME_TTL;          // :67-68
try { feed = productFeedClient.homeFeed(SECTION_SIZE); }  // :70
catch (ProductFeedUnavailableException e) {               // :71
    log.warn("首页商品区块降级(商品域不可用): {}", e.getMessage());   // :73  ← 降级判据：一请求一条 WARN
    ttl = HOME_DEGRADED_TTL;                              // :74  ← 降级档 TTL
}
HomeData data = HomeData.builder().banners(banners()).notices(notices())
        .categories(feed == null ? List.of() : emptyIfNull(feed.getCategories()))     // :80
        .hotProducts(feed == null ? List.of() : emptyIfNull(feed.getHotProducts()))   // :81
        .newProducts(feed == null ? List.of() : emptyIfNull(feed.getNewProducts()))   // :82
        .build();
cacheService.setJson(CacheKeys.homeIndex(), data, ttl);   // :84
```

**不变量与契约**：

1. **fail-open 成空数组，绝不 5xx**：只捕获 `ProductFeedUnavailableException`（`:71`），三个商品区块落成 `List.of()` 而**不是 null**（前端空数据兜底依赖这点，`HomeAggregationMySqlTest:40-41` 的注释写明）；HTTP 200 + `code=0`。
2. **`catch` 范围刻意窄**：异常是独立类（`ProductFeedUnavailableException:6-9` 说明"不能顺手把本服务自己的 bug 也吞成首页少了商品区块"）⇒ 本服务的 NPE/序列化错照常冒到 `GlobalExceptionHandler` 变 500，不伪装成降级。
3. **两档 TTL 靠"同一个 key + 不同 TTL"区分**，没有降级标记位：正常 45s / 降级 5s（`:50,53,68,74,84`）——既不把故障期每个请求变成一次 2.5s 超时，也不让首页在商品域恢复后长时间停在降级态（`:33-36`）。
4. **先远程、再查本库，且 `home()` 不加 `@Transactional`**（`:39-40`）：远程最长 2.5s，不该占着数据库连接；本域两次读各自 `@Transactional(readOnly = true)`（`:89`、`:106`）。
5. **本域读的口径**：`status = 1` + `sort ASC, id ASC` + `LIMIT 0,8`（`:91-94`、`:108-111`）。
6. **区块条数固定 8**，测试用 `ArgumentCaptor` 钉住（`HomeAggregationMySqlTest:79-81`）。

### 3.5 `AdminContentServiceImpl`（202 行）

轮播/公告的后台 CRUD + **每次写操作后删首页缓存**。

| 方法 | 关键行为 | 缓存失效 |
|---|---|---|
| `bannerPage`（`:42-54`）/ `noticePage`（`:106-118`） | `keyword` 模糊、`status` 精确、`sort/id ASC`；`PageKit.page`（上限 10000）与 `PageKit.size(_, 50)` 收敛入参（`:45-46`、`:109-110`），再拼 `LIMIT (page-1)*size, size`（`:52`、`:116`） | — |
| `createBanner`（`:56-65`） | 校验 → 填充 → `status` 默认 `ENABLED`（`:61`）→ insert → 返回自增 id | `:63` |
| `updateBanner`（`:67-84`） | 逐字段判空覆盖（`hasText` 才覆盖 title/imageUrl）⇒ PATCH 语义 | `:83` |
| `updateBannerStatus`（`:86-95`） | `requireBanner` → `checkStatus` → 只 set id+status 的 `updateById` | `:94` |
| `deleteBanner`（`:97-102`） | `requireBanner` → `deleteById` | `:101` |
| `createNotice`（`:120-132`） | `requestValidator.check` → `sort` 默认 0、`status` 默认 `ENABLED`、**`publishTime = now()`**（`:128`） | `:130` |
| `updateNotice`（`:134-148`）/ `updateNoticeStatus`（`:150-159`）/ `deleteNotice`（`:161-166`） | 与 Banner 对称；`updateNotice` **不改** `publishTime` | `:147` / `:158` / `:165` |

- **8 个写方法，8 处 `cacheService.delete(CacheKeys.homeIndex())`**（`:63,83,94,101,130,147,158,165`），顺序是"先写库、再删缓存"（cache-aside）；写方法**没有 `@Transactional`**（只有两个 page 是 `readOnly = true`）⇒ 单条语句先自动提交，不存在"事务未提交就删缓存"的窗口，代价是**没有补偿**：删除失败被 `CacheService` fail-open 吞掉（`CacheService:123-137` → `degrade` → 一条 WARN + 30s 退避），前台最长 45 秒（＋抖动）后自然过期。
- **错误文案逐字**（C1）：`轮播不存在`（`:184`，404）、`公告不存在`（`:192`，404）、`状态值仅支持 0/1`（`:199`，400）；由 `InternalContentApiMySqlTest#errorMessagesUnchanged:157-181` 钉住。
- **校验收口**：`createBanner`/`createNotice` 走 `RequestValidator#check`（DTO 上的 `@NotBlank`），`updateXxx` **不调** `check`（"改标题为空串"既不会 400 也不会清空标题——`hasText("") == false` ⇒ 该字段被跳过）。
- **状态极性**：`EnableStatus.DISABLED=0 / ENABLED=1`（`EnableStatus:24-25`），`checkStatus` 只放行这两个值。

- 分页 wrapper **复用同一实例**：`selectCount(wrapper)` 在 `selectList(wrapper.last("LIMIT …"))` **之前**（`:51-52`、`:115-116`）——顺序反了会让 count 带上 LIMIT。

### 3.6 `ProductFeedApi`（51 行）+ `ProductFeedClient`（103 行）+ `ProductFeedUnavailableException`（20 行）

本服务**唯一的出站调用**——商品域的首页商品区块（`GET /internal/v1/product/home-feed?size=8`）。

- `ProductFeedApi`：`@HttpExchange(url = "/internal/v1/product", contentType = "application/json")`（`:41`）+ `@GetExchange("/home-feed") ApiResponse<HomeFeedVO> homeFeed(@RequestParam("size") int size)`（`:49-50`）。返回类型是**下游原始响应体** `ApiResponse<T>`（`:36-37`），解包留给客户端类；这一层不做错误语义/日志/降级（`:28-34`）。
- `ProductFeedClient` 构造时装配连接（`:67-78`）：`restClients.build(loadBalancedBuilder, baseUrl, connectTimeoutMs, readTimeoutMs)`（`:72`）→ `HttpServiceProxyFactory.builderFor(RestClientAdapter.create(restClient)).build().createClient(ProductFeedApi.class)`（`:73-75`）。配置键与默认值：`mall.product.base-url` = `lb://mall-product`、`connect-timeout-ms` = **300**、`read-timeout-ms` = **2500**（`:69-71`）。
- **超时为什么是 300/2500**（`:48-56`）：P2 实测"下游冷启动首次调用 1.98s / 冷缓存 ~545ms / 稳态 18~40ms"，300ms 会把**正常的冷启动请求**判成故障 ⇒ 每次下游重启后第一个访客看到没有商品的首页；代价只在"下游卡死但不拒绝连接"时体现（最多等 2.5s 再降级，随后 5s 降级缓存兜住）。`http://` 开头时绕过服务发现直连（排障/演练，`:44-46`），由 `OutboundRestClientFactory:45-47` 显式挂同一个头拦截器。

**`homeFeed(int size)` 的三条文案（逐字，`:86-102`）**：

| 触发 | 异常与文案 |
|---|---|
| 传输异常/超时/5xx/反序列化失败（`catch (Exception e)`，`:90`） | `ProductFeedUnavailableException("调用商品域首页区块失败: " + e, e)`（`:92`） |
| 响应体为 null（`:94`） | `ProductFeedUnavailableException("商品域返回空响应体")`（`:95`） |
| 业务码非 0（`:97`） | `ProductFeedUnavailableException("商品域返回业务错误: code=" + code + ", message=" + message)`（`:98-99`） |

**契约**：本类**不返回 null、不吞异常**（`:25-26`）——"下游挂了"与"首页本来就没商品"必须能区分，这正是 `HomeServiceImpl` 能安全降级的前提。为什么在 HTTP Interface 之上仍保留这个类（`:40-43`）：调用方 `HomeServiceImpl` 与真库套件的 `@MockitoBean ProductFeedClient` 都对着**这个类**，保留它 ⇒ 服务层与测试一行不用改。

### 3.7 `FileStorageService`（104 行）

把字节写进 MinIO 并返回公网 URL；桶自动创建 + 首次使用时设为"公开只读"。

- 构造（`:31-36`）：`endpoint` 去尾斜杠（`:94-99`，null 回落 `http://127.0.0.1:9000`）、`bucket` 默认 `mall`（`:35`）。
- **对象命名规律**（`:46-49`，代码里能读到的全部路径拼接）：

```java
String datePath   = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy/MM/dd"));  // 例 2026/09/15
String objectName = datePath + "/" + UUID.randomUUID().toString().replace("-", "") + "." + type.extension();
// 例：2026/09/15/<32 位无连字符 uuid>.png；URL = endpoint + "/" + bucket + "/" + objectName（:61）
```

  **后缀取自魔数识别结果**（`type.extension()`），**不沿用原始文件名**——原始名只在返回体 `name` 里回给前端（缺省 `"file"`，`:46`）。
- 写入：`putObject(stream(in, file.getSize(), -1), contentType = type.contentType())`（`:51-56`）——大小已知故分段 `-1`，Content-Type 用识别结果而非客户端声明值。
- 桶初始化 `ensureBucket()`（`:65-92`）：`volatile bucketReady` + 双重检查 + `synchronized(lock)` ⇒ 每 JVM 只做一次；不存在则 `makeBucket`，再 `setBucketPolicy` 设为公开只读（注释写明"仅允许 `s3:GetObject`"，策略 JSON 在 `:80-84`）。
- 失败语义：`putObject` 异常 → `log.error("MinIO 上传失败", e)` + `BusinessException(500, "上传失败，请确认 MinIO 已启动")`（`:57-60`）；`ensureBucket` 异常 → `BusinessException(500, "连接 MinIO 失败：" + e.getMessage())`（`:88-90`）——**设策略失败也落到这条"连接失败"文案**。
- 返回记录：`record UploadResult(String url, String name, long size, String contentType)`（`:102`）；`size` 是收到的字节数。

### 3.8 `ImageTypeDetector`（87 行）

**按文件头（魔数）**识别 JPEG/PNG/GIF/WebP，识别不出返回 null。为什么不能只信 `MultipartFile#getContentType`（`:9-11`）：那是客户端自己填的字符串，改个请求头就能把 html/js/svg 声明成 `image/png` 存进公开桶。

- `detect(InputStream)`（`:49-63`）只读**前 12 字节**（循环读满或到 EOF），`read < 4` ⇒ null，**不关闭流**（调用方 `try-with-resources` 管）。
- `detect(byte[], int)`（`:65-86`）四条判据：JPEG `FF D8 FF`（≥3）、PNG `89 50 4E 47 0D 0A 1A 0A`（≥8）、GIF `GIF87a|GIF89a`（≥6）、WebP `RIFF…WEBP`（≥12）。
- `enum ImageType`（`:17-38`）把"后缀 + Content-Type"绑在一起：`JPEG→(jpg,image/jpeg)`、`PNG→(png,image/png)`、`GIF→(gif,image/gif)`、`WEBP→(webp,image/webp)`。**没有"未知类型放行"的分支**。

### 3.9 `MinioConfig`（22 行）+ `MinioProperties`（14 行）

`MinioProperties` 是 `@ConfigurationProperties(prefix = "mall.minio")` 的 record，四字段 `endpoint/accessKey/secretKey/bucket`（`:8-13`）**无默认值**；`MinioConfig` 用 `@EnableConfigurationProperties` + `@Bean MinioClient`（`:11-21`）直接取这三个值 ⇒ 缺 `endpoint`/`access-key`/`secret-key` 会在**启动时**失败（与 `FileStorageService` 里 endpoint/bucket 的兜底不同，那两个只影响拼 URL）。
⚠️ **位置澄清**：本模块**没有** `upload/MinioConfig.java`——两个 MinIO 配置类在 `support/` 包（`support/MinioConfig.java`、`support/MinioProperties.java`），`upload/` 只有 `FileStorageService` 与 `ImageTypeDetector`。

### 5.1 出站（`*Api` + `*Client` 成对）

## 9. 坑与已知边界

1. ~~**`V1__baseline.sql:32` 的 `cms_notice.id` 缺 `AUTO_INCREMENT`**~~ ⇒ **❌ 更正（复核发现这是误报，不要按它去改基线）**：
   实测 `V1__baseline.sql:32` = `` `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键' ``（含 `AUTO_INCREMENT`），
   运行库 `information_schema.columns` 也实测 `cms_notice.id → extra=auto_increment`、`column_type=bigint`。
   原文那句"缺 AUTO_INCREMENT"是**读文件读错**（把它与 `cms_banner` 的行号混了：`cms_banner.id` 在 `:16`，`cms_notice.id` 在 `:32`，两者**都有** `AUTO_INCREMENT`）。
   ✅ 保留下来的、经复核成立的观察是：**`cms_notice` 的表级 `AUTO_INCREMENT` 起始值不同**（`cms_notice → AUTO_INCREMENT=109`、`cms_banner → 197`，见 `V1__baseline.sql:42/27`）——
   这只是"历史插入过多少行"的痕迹，不构成缺陷。
2. **首页缓存命中时不校验商品域**：`HomeServiceImpl:62-65` 命中即返回 ⇒ 商品域挂掉后的 45 秒内，缓存里的商品区块照旧返回（是"旧数据"而不是空数组）；降级只在**未命中**时发生。
3. **降级态与正常态共用一个 key**，只靠 TTL 长短区分，没有降级标记位（`:50,53`）⇒ 外部（`redis-cli GET`）看不出当前是否降级，只能看 TTL 或日志里的 WARN。
4. **`CacheService` 会给 TTL 打 ±15% 抖动**（`CacheService:256-262`，下限 1000ms）⇒ 代码注释里的"45 秒/5 秒"是**名义值**；用 TTL 做断言要留余量。
5. **写操作无事务、删缓存无补偿**：`AdminContentServiceImpl` 写方法没有 `@Transactional`（只有两个 page 是 `readOnly = true`），"写库 → 删缓存"两步之间无回滚；删缓存失败被 fail-open 吞掉（只有 WARN），前台靠 TTL 自然过期。
6. **`update` 系列不触发 Bean Validation**：`updateBanner`/`updateNotice` 不调 `RequestValidator#check`，逐字段判 `hasText`/`!= null`（`:70-81,137-145`）⇒ PATCH 语义，且**没有"清空字段"的能力**（传空串等于不改）。
7. **分页 wrapper 复用**：`selectCount(wrapper)` 必须排在 `selectList(wrapper.last("LIMIT …"))` **之前**（`:51-52`、`:115-116`），顺序调换会让 count 带上 `LIMIT`。
8. **两套大小上限口径不同**：容器 10MB 与业务 5MB（§3.3）⇒ 5~10MB 之间由本服务的 400 文案拒绝，>10MB 由容器先行拒绝、走不到这条文案。
9. **MinIO 桶策略每 JVM 只设置一次**（`FileStorageService:29,65-92` 的 `bucketReady`），之后不再校验；多实例并发首次都会 `setBucketPolicy`（幂等），失败文案是"连接 MinIO 失败"而不是"设置桶策略失败"。
10. **`ImageTypeDetector` 只读前 12 字节**且 `read < 4` 即判不可识别（`:50-63`）⇒ 极短文件的错误也是"仅支持 jpg/png/webp/gif 图片"这条文案，不区分"太短"与"类型不对"。
11. **扫描面只有 `com.mall.content.**`**（`ContentApplication:17`）：新增 `config` 类必须在这个包下；共享内核 bean 来自 `mall-common` 自动装配（§0），**不要**在本服务重复声明——`MallCommonAutoConfiguration` 全系 `@ConditionalOnMissingBean`，自建同名 bean 会静默覆盖共享版行为。
12. **`publish_time` 只在新建时写 `now()`**（`AdminContentServiceImpl:128`），更新不改；前台 `NoticeVO` 返回的是 `createTime`（`HomeServiceImpl:116`、`NoticeVO:15`）⇒ 该列目前对前台无影响。
13. **写路径不校验调用方身份**（只有共享密钥），也无法区分"是哪个管理员改的"——审计信息不在本域（`WebConfig:11-14` 记录了退场条件）。
