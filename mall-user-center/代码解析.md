## 2. 分层与包职责

- **`controller` / `internal`**：只做参数搬运 + 调 Service，**零业务判断**。两者分开是为了让"服务间入口"在包名上可见。ArchUnit 钉住 `controller` 只放 `*Controller`（`architecture/CodeStyleTest#controllerNaming`）。
- **`service`**：接口只收发 DTO（`service/MemberQueryService:17-22` 明写"不含 Entity、不含 Mapper、不含 `LambdaQueryWrapper`"），目的是"可一对一变 HTTP"。
- **`service.impl`**：全部业务规则。命名口径见 `CodeStyleTest#serviceNaming`：接口 `*Service`、实现 `*ServiceImpl`。
- **`domain` / `mapper`**：实体与 `BaseMapper`。`CodeStyleTest#domainDoesNotDependOnOuterLayers` 禁止 domain 依赖 controller/internal/client/service。
- **`support`**：契约面副本 + 无业务语义的工具/常量。`CodeStyleTest#supportDoesNotDependOnOuterLayers` 禁止它依赖外层——**这就是 `CacheKeys`/`MqTopology` 只放常量、Bean 放 `config` 的原因**（`support/MqTopology:35-36`）。
- **`support/dto`**：跨服务契约快照，注释统一标注"字段形状与 XX 端点逐字一致"。
- **`client`**：`CodeStyleTest#clientNaming` 只允许 `*Api`（声明式接口）/`*Client`（域语义）/`*Factory|*Interceptor`（装配）/`*Exception`。
- **`mq`**：`CodeStyleTest#mqNaming` 只允许 `*Consumer`/`*Publisher`/`*Message`/`*Config`/`*Topology`/`*Messages`。
- **组装根 = `config` 包（不是 `app/`）**：`WebConfig`、`MybatisPlusConfig`、`BcryptConfig`、`LoadBalancedClientConfig`、`RabbitMqConfig`、`OpenApiConfig`。

## 3. 核心类详解（15 个）

### 3.1 `config/WebConfig`（68 行）——身份与内部闸门的接线处

- `addInterceptors`（`:38-41`）：只给 `/internal/**` 挂 `InternalApiAuthInterceptor`。
- `addArgumentResolvers`（`:51-67`）：匿名 `HandlerMethodArgumentResolver`，判据 `hasParameterAnnotation(MemberId.class) && Long.class.equals(parameter.getParameterType())`（`:55-56`）。**只支持包装类型 `Long`**：写成基本类型 `long` 解析不到（`:47-48` 注释明说"不要静默注入一个 0"）。

### 3.5 `support/TokenVersionService`（58 行）——无状态 JWT 的主动失效

```java
private static final Duration TTL = Duration.ofDays(30);              // :25
public long current(String type, long userId) { ... }                // :33-43  null ⇒ 0；非数字 ⇒ 0
public long bump(String type, long userId) {                         // :46-49
    long v = cacheService.increment(CacheKeys.tokenVersion(type, userId), TTL);  // INCR + TTL
    return v < 0 ? 0L : v;
}
public boolean matches(String type, long userId, long tokenVer) {     // :52-57
    if (!cacheService.available()) return true;                       // Redis 挂 ⇒ fail-open
    return current(type, userId) == tokenVer;
}
```

- **key**：`CacheKeys.tokenVersion` = `"mall:" + "token:ver:" + type + ":" + userId` ⇒ **`mall:token:ver:user:{id}`**（`support/CacheKeys:29`）。`CacheKeys:8-16` 写明这一串**与网关逐字相同**，改一侧必须同时改另一侧。
- **TTL 30 天**（`:18` 注释）：到期回到版本 0，旧 token（`ver` 已是 N）被判为不等 ⇒ 用户重新登录即可。
- **`matches` 三条口径**：Redis 不可用 ⇒ `true`（不因缓存故障把全体用户踢下线）；键不存在 ⇒ 0；值非数字 ⇒ 0。
- ⚠️ 生产代码里 **`matches` 没有任何调用方**（只在 `AuthEndToEndMySqlTest:123,152` 用来断言"版本已失效"）——真正比对在网关；`TYPE_ADMIN`（`:28`）在本服务同样无调用方。
- 写入方三处：`MemberServiceImpl:112`（登出）、`:138`（改密）、`MemberAdminServiceImpl:49`（禁用）。

### 3.6 `support/MemberStatusCache`（54 行）——**只删不写**的状态加速层

- `get`（`:35-37`）`getJson(CacheKeys.memberStatus(id), MemberStatusVO.class)`；`put`（`:40-42`）`setJson(..., TTL=10min)`（`:30`）；`evict`（`:51-53`）`cacheService.delete(...)`。
- **key**：`CacheKeys.memberStatus` = `"mall:cache:member:status:" + memberId`（`support/CacheKeys:34`）。
- **"只删不写"的理由（注释原话 `:44-49`）**：`evict` **不负责"立即踢下线"**——那是 `TokenVersionService#bump` 的活（网关比对版本号后直接 401）；本缓存只是状态读取的加速层。删除而非改写是为了"避免写了一份旧的进去"这类难查的脏缓存（`MemberAdminServiceImpl:43` 有同一句原话）。TTL 10 分钟是第二层保险。
- ⚠️ **本模块内只有 `evict` 有调用方**（`MemberAdminServiceImpl:44`）；`get`/`put` **无任何调用方**。读方是网关与各服务的 `MemberSession`；类注释 `:39` 说的"回填"在当前代码里没有落点（`MemberStatusServiceImpl:37-40` 只产出 `MemberStatusVO`，不写缓存）。

### 3.7 `support/JwtUtil`（161 行）——本服务的 HS256 签发方

- **构造即 fail-fast**（`:42-48`）：`mall.jwt.secret` 空 ⇒ `IllegalStateException`；`trim().length() < 32` ⇒ 也拒绝启动。理由（注释）：以前缺配置会静默用仓库里公开的兜底密钥签发 token，**任何人都能自签一个 admin token**。
- `createToken(userId, username, type, ver)`（`:58-70`）：手拼 payload `{"sub","name","typ","ver","iat","exp"}`，`exp = now + expireHours*3600`。`:55-56` 明写"**不要写死 0**"：版本号必须来自 `TokenVersionService#current`。
- `parse`（`:73-105`）：段落数必须 3；签名用 `MessageDigest.isEqual` 常量时间比对（`:82`、`:145`）；`sub`/`exp` 必需；`exp < now` 才算过期（`:97`，用 `<` 而非 `<=`）；`ver` 缺失按 0（`:107-110`）。解析用**正则**抽 JSON 字段（`:27-32`），不引 JSON 解析器。
- 非法/过期统一抛 `BusinessException(401,"登录已失效，请重新登录")`（`:154-156`）。
- ⚠️ **`parse` 生产代码也无调用方**（只在 `MemberAuthMySqlTest:79`、`AuthEndToEndMySqlTest:89,139` 断言签发结果）。本类真正的生产职责只有 `createToken`（`MemberServiceImpl:144`）。

### 3.8 `service/impl/MemberAdminServiceImpl`（52 行）——禁用时两件事的分工


### 5.3 MQ 拓扑与兜底

| 角色 | 名字 | 出处 |
|---|---|---|
| 交换机（**与单体共享，声明参数必须一致**：topic + durable + 无 arguments） | `mall.oms.event` | `MqTopology:46`、`RabbitMqConfig:49` |
| 业务路由键 | `order.paid` / `order.shipped` / `refund.settled` | `MqTopology:48-50`、绑定 `RabbitMqConfig:64-76` |
| 本服务工作队列 | `mall.user.notification` | `MqTopology:55`、`RabbitMqConfig:57-61` |
| 重试队列（无消费者，消息自带 TTL 到期死信回工作队列） | `mall.user.notification.retry` | `MqTopology:57`、`RabbitMqConfig:96-106` |
| 死信队列（无消费者，仅供观测与人工重投） | `mall.user.notification.dlq` | `MqTopology:59`、`RabbitMqConfig:111-118` |
| 本服务私有路由键 | `notification.retry` / `notification.redeliver` / `notification.dlq` | `MqTopology:68-72` |

- **为什么是独立队列而不是复用单体的 `mall.oms.events`**（`MqTopology:18-20`）：同名队列 = 竞争消费，一条消息只会被其中一个服务拿到 ⇒ 通知或统计**随机各丢一半**。
- **为什么键名刻意不与单体的 `event.retry/redeliver/dlq` 同名**（`MqTopology:61-67`）：共用 `event.dlq` 会让双方死信互相扇出（观测串味、人工重投可能重投别人的消息）。
- **为什么每条消息带 TTL 而不是队列级 `x-message-ttl`**（`RabbitMqConfig:88-92`）：队列参数一旦声明就不能改，会把重试间隔锁死在队列定义上。
- 失败路径：`OrderEventRetryPublisher`（79 行）三个方法 `publishRetry`/`publishToDlq`/`publishRawToDlq` **全部 `try/catch` 后只打日志**（fail-open，`:46-49,60-62,71-73`）——此时消息已被 ack，不会毒住队列。
- 消费端口径：`acknowledge-mode: manual`、`prefetch: 10`、`concurrency: 1`、`max-concurrency: 2`（`application.yaml:23-29`）。

## 9. 坑与已知边界

**A. 死代码与过期注释（改代码前先知道，别被误导）**

1. **`support/AuthToken`/`support/AuthHeader` 是残留**：`AuthToken` 无任何使用处，其 javadoc 指向**不存在的包** `com.mall.usercenter.auth.support.MemberIdArgumentResolver`（`AuthToken.java:12`）；`AuthHeader#bearer` 同样无调用方。`OpenApiConfig:67` 的 `INJECTED_PARAM_NAMES` 里还留着 `"token"` 就是为了它们。
2. **`TokenVersionService#matches`/`JwtUtil#parse` 生产代码无调用方**（只有测试在用，真正的验签与比对在网关）；`TYPE_ADMIN`（`JwtUtil:25`、`TokenVersionService:28`）也无调用方——本服务只签发 `user` 令牌。
3. **`MemberStatusCache#get`/`#put` 在本服务无调用方**，只有 `evict` 被调；类注释 `:39` 说的"回填（会员注册/登录/读取后调用）"在当前代码里没有落点；`MemberStatusVO:10` 也说"写入方只有一个——本服务（login/logout/改密/禁用/资料变更时刷新）"，同样查无实现。
4. **`OpenApiConfig` 整体是单体遗留**：示例路径 `/api/admin/product/**`、`/api/admin/category/**`（`:93-119`）、端口 `localhost:8080`（`:26-27`）、`PRODUCT_BODY_EXAMPLE`（`:40-56`）全部指向**本服务不存在的端点**。对它唯一还生效的是"摘掉 `@MemberId` 渲染出的伪 query 参数"（`:127-135`）。
5. **`AddressQueryServiceImpl:26`** 带 `@ConditionalOnProperty(name="mall.user-center.remote", havingValue="false", matchIfMissing=true)`——**单体侧过渡期开关的副本**，其注释（`:19-25`）讲的也是"单体侧为什么用开关"，放在属主服务里没有对应关系；同一行还把注解与 `@Service` 挤在一起。
6. **`pom.xml` 头部注释（`:8-13`）说"本服务不依赖单体、共享内核都是自持副本"，与 `:172-176` 起依赖 `com.mall:mall-common` 矛盾**；pom 里还有 `mall_content`/`mall-content`（`:72`、`:134`）的复制残留。实际自持的只有契约面（`CodeStyleTest:20-21` 明说 `ApiResponse`/`BusinessException`/`GlobalExceptionHandler` 刻意各服务自持）。
7. **`EnableStatus` 的 javadoc 引用不存在的包**（`:19-20`：`com.mall.usercenter.pms.support.CommentStatus`、`sms.support.CouponStatus`），并举了本服务不持有的 `sys_user`、`pms_*`、`cms_*` 列（`:8-15`）。
8. **`ProductSnapshotClient` 类注释仍写"地址走服务发现（`lb://mall-legacy`）"**（`:29`），而配置默认值已是 `lb://mall-product`（`:76`）——以配置为准。

**B. 语义上容易写错的点**

9. **`login` 先验密码、后验状态**（`MemberServiceImpl:97`→`:100`）：被禁用 + 密码错的账号得到「用户名或密码错误」。
10. **`bump` 不参与本地事务回滚**：`changePassword`（`MemberServiceImpl:135-138`）与 `updateStatus`（`MemberAdminServiceImpl:42-49`）都是"先落库、后 bump"，而 `bump` 走 Redis。
11. **`removeItem`/`removeChecked` 没有 `@Transactional`**（`CartServiceImpl:161-171`）。
12. **`count` 是数量之和**（`CartServiceImpl:178`）：加购 3 件同一 SKU 让角标变 3 而不是 1。
13. **`CartServiceImpl:135-136`**：`sku == null ⇒ stock = 0` ⇒ 数量校验必失败（409「库存不足」）；但 `sku()` 抛 `ProductUnavailableException` 时**不降级**，所以 `null` 只可能来自"下游明确回答没有"。
14. **同一个 `spu()` 调用有两种处理**：`FavoriteServiceImpl#toggleFavorite:47-49` 抛 404，`#recordFootprint:93-96` **静默 return**（不报错也不记录）。
15. **`ums_member` 的逻辑删除让"被删除会员"与"不存在会员"对外完全同形**（`MemberStatusServiceImpl:18-20`）：都是 401「登录已失效，请重新登录」/ `data: null`。
16. **内部端点"不存在"一律 `data: null` 而非 404**（`InternalUserController:106-107`、`:154-155`）：调用方必须用"返回条数是否等于请求条数"判断非法 id（`CartCheckoutService:33-34`）。

**C. 边界（它**不做**什么）**

17. **不验签、不持有验签逻辑**：`Authorization` 头**不是**身份来源（`GatewayIdentityResolverTest:98` 钉住）；令牌校验与版本比对都在网关。
18. **不碰商品表**：价格/库存/上下架/规格全经 `ProductSnapshotClient`；**库存扣减与下单时的价格重算都在商品域**（`CartServiceImpl:39-40`、`CartCheckoutServiceImpl:24-25`）。
19. **不写订单、不做库存/价格校验**：结算只提供 `claim`/`restore` 两件事（`CartCheckoutService:13-15`）。
20. **不做后台登录**：没有 `sys_user` 相关端点/表，管理端登录属 `mall-admin`。
21. **不写商品索引、不算订单日统计**：MQ 消费的唯一副作用是 `ums_notification`（`NotificationEventConsumer:24`）。
22. **不靠 `mall:cache:member:status:{id}` 判身份**：身份只来自请求头（`GatewayIdentityResolver:36-38`）。
