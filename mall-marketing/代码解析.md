## 2. 分层与包职责

- **`controller/` 与 `internal/` 是两个面、不是两层**：前者 `@MemberId`（会员以自己身份领券），后者 `X-Internal-Token`（trade 代用户锁券）；`memberId` 来源不同，**这就是它们不能合成一个接口的原因**（`service/CouponMemberService.java:13-22`）。
- **`service/` 按"谁在调"切分**：`CouponMemberService`（会员 HTTP 面）、`CouponQueryService`（读：算钱）、`CouponCommandService`（写：改状态）、`AdminCouponService`（后台）；`service/impl/` 只放对应实现。
- **`mapper/` 承担状态机**：`CouponMemberMapper` 手写 6 条 SQL，刻意**不用** `updateById`——它按主键无条件覆盖，表达不出"只有当前是 X 才改成 Y"（`CouponMemberMapper.java:39-40`）。
- **`support/` 放纯函数与自持契约副本**：`CouponRules`（纯判断，不查库不抛异常）、`CouponStatusProjection`（三态投影）、`ApiResponse`/`BusinessException`/`GlobalExceptionHandler`/`PageResult`（与其它服务逐字同构的自持副本，不共享 jar）。
- **组装根在 `config/`**：`MybatisPlusConfig`（手写 `MybatisSqlSessionFactoryBean`，`@MapperScan("com.mall.marketing.mapper")` 只扫 mapper 包，好让"误标 `@Mapper`"立刻暴露，L15-19）、`WebConfig`、`RabbitMqConfig`。每个模块自带组装根、没有聚合 pom。
- **架构规则由 `architecture/CodeStyleTest`（ArchUnit，10 例）守**：`dto`/`client`/`controller`/`mapper`/`task`/`mq`/`config` 的命名后缀白名单；`service.impl` 以 `Service` 结尾；两条依赖方向——**`domain` 与 `support` 都不得依赖 `controller/internal/client/service`**。
- **本服务不做的事**：不查 `ums_member`/订单表（跨域），不写券以外的表，不持有登录态（只信网关注入头），不做业务缓存（读路径直查库），无 springdoc（`pom.xml:17-18`）。

## 3. 核心类详解

### 3.1 `controller/CouponController`（71 行）
会员侧唯一入口，三个方法各自一行委托 `CouponMemberService`。`receive` 带 `@RateLimit(scope="coupon_receive", limit=10, windowSeconds=60, by=USER)`（L59）。
**契约**：注解参数与单体**逐字相同**（`scope` 是 Redis 键名的一部分、`by=USER` 决定按会员维度计数），改任何一个都是改对外行为（类注释 L54-56）。测试 `CouponMemberApiMySqlTest`（17 例）。

### 3.2 `internal/InternalMarketingCouponController`（124 行）
5 个端点，`check` → Service → `ApiResponse.ok(...)`。包装类型固定：`lock` → `CouponLockResult{"locked":bool}`，`use`/`unlock` → `CouponChangeResult{"changed":bool}`（两端点同形）。
`usable` 只返回 `coupon_status=0`（**锁定中的券不是可用券**）；`discount` 的 `couponMemberId` 可为 null（= 不用券 → `data:0`）。测试 `InternalMarketingCouponApiMySqlTest`（14 例）。

### 3.3 `internal/InternalMarketingAdminCouponController`（117 行）
7 个端点；`page`/`records` 的 `pageNum`/`pageSize` 为空时由 `orDefault(...)`（L114-116）补 1/10（与单体 `PageQuery` 同口径），`records` 的 body 可整个缺失（`@RequestBody(required=false)`，L106）。
`page` 直接返回 `Coupon` 实体（JSON 字段名与单体后台逐字一致）。404/409/400 文案全由 Service 抛、这里**不转换**——包成 500 会让后台页面从"这条券删不了"变成"系统繁忙"（类注释 L49-50）。测试 `InternalMarketingAdminCouponApiMySqlTest`（9 例）。

### 3.4 `service/impl/CouponCommandServiceImpl`（194 行）——**本模块最重要的类**

**`lock(memberId, couponMemberId, orderNo)`：判定顺序即契约**（每一步对应一条对外文案）

| # | 判据 | 结果 | 行 |
|---|---|---|---|
| 0 | 任一参数 null/空白 | `false`，**一次库都不写**（绝不写出没有归属的锁定券） | L68-72 |
| 1 | 券不存在 **或** 不属于该会员 | 400「优惠券不可用」（**不区分**两者，避免探测别人的券 id） | L74-76 |
| 2 | 已被**本单**锁定（`CouponRules.lockedBy`） | `true`（**幂等**，重试不会得到 409） | L78-80 |
| 3 | 状态 ≠ `UNUSED(0)`（别人锁的/已核销/已过期状态） | 409「优惠券已被使用或失效」 | L81-83 |
| 4 | 单券过期 / 模板停用 / 模板不在有效窗内 | 400「优惠券已过期」/「优惠券已停用」/「优惠券已过期」 | L84-94 |
| 5 | **CAS `0 → 3`**（`lockUnused`） | 影响 1 行 = 抢到 → `true` | L99-102 |
| 6 | 影响 0 行 → `selectCurrentById`（`FOR SHARE`）重读 | 若是"本单已锁" → `true`；否则 409 | L107-111 |

```java
int claimed = couponMemberMapper.lockUnused(couponMemberId, memberId, orderNo, now);
if (claimed == 1) { return true; }
CouponMember after = couponMemberMapper.selectCurrentById(couponMemberId);  // 当前读，不是快照读
if (CouponRules.lockedBy(after, orderNo)) { return true; }
throw new BusinessException(409, "优惠券已被使用或失效");
```

- **"影响行数即并发凭证"**：真正的判定只在第 5 步；第 2/3 步的读**只决定给哪条文案**，读错最坏是"文案不够精确（409 vs 400）"，而不是"一张券被锁两次"（类注释 L43-46）。并发下"只有一方拿到"是数据库保证的，不是应用层判出来的。
- **`lock_time` 与 `order_no` 在同一条 UPDATE 里写**（`CouponMemberMapper.java:51-53`）：不存在"锁上了但没记时间/单号"的中间态——否则每日对账永远找不到这张券，它只会烂在库里（L96-98）。
- **⚠️ `lock` 里没有门槛校验（刻意）**：契约 `CouponLockRequest` 没有 `goodsTotal`，门槛由同一次下单里先行的 `discount`/`usable` 按金额判过；两处都拦会变成两套口径，而"金额"只有 trade 知道（L37-41）。

**`use(...)`**：`markUsed` CAS `3 → 1`（`order_no` 必须匹配）→ 1 行即 `true`；0 行时用 `selectCurrentById` 兜底，只有"状态是本单的 `USED`"才 `true`（L128-133）。
**重复 use 不刷新 `use_time`**——0 行时根本没执行 UPDATE（`CouponMemberMapper.java:66-67`）。

**`unlock(...)`**：`markUnused` CAS `3 → 0` 且清 `order_no`/`lock_time`；0 行时兜底**只把"当前就是 `UNUSED`"算成功**（L148-154）：
刻意**不**把 `USED` 算成功（那等于谎报"券已回滚"，其实已被核销），也刻意**不**把"LOCKED-by-别人"算成功（那等于解锁了别人的券）。
⚠️ 澄清一处常见误读：**正常 `unlock` 路径没有 `lock_time` 阈值**，它靠 `order_no` 精确定位自己锁的那张；阈值只出现在下面的对账路径。

**`unlockStuckLocks(limit)` —— 每日对账口径**（L171-193）：

1. `cap = limit <= 0 ? 200 : limit`（L174）；`threshold = now - max(1, stuckLockHours)`（L175），`stuckLockHours` = `@Value("${mall.marketing.stuck-lock-hours:2}")`（L62-63）。
2. `selectStuckLocked(threshold, cap)`：`coupon_status=3 AND (lock_time IS NULL OR lock_time < threshold)`，排序 `ORDER BY (lock_time IS NULL) DESC, lock_time ASC`（`CouponMemberMapper.java:127-131`）。**`lock_time IS NULL` 的 LOCKED 行也算"锁太久"**——那是加列前的历史遗留行，只按时间筛会永远漏掉。
3. 逐行 `unlockStuck(id, threshold)`：**读与写用同一阈值** ⇒ "对账跑到一半时用户刚锁上的券"不可能被误放（它的 `lock_time` 必然晚于阈值，`CouponMemberMapper.java:149-158`）。
4. 每解一行打 WARN（`memberId`/券 id/`orderNo`/`lockTime`/阈值，L185-186），末尾再打本轮汇总（L190）。**必须留痕**：对账解的都是"本该由关单路径解开却没解"的异常行，否则"券莫名回到未使用"会变成无法追查的黑盒（L165-167）。
5. **幂等**：重复执行只解剩下的行；一条都没解到时返回 0、不产生日志噪音。

测试 `coupon/CouponTriStateMySqlTest`（26 例，含 8 线程并发"只有一方拿到"、同单号并发幂等、lock/unlock 竞争后终态自洽）。

### 3.5 `mapper/CouponMemberMapper`（201 行）——**状态机本体**

| SQL | 语义 | 关键条件 | 行 |
|---|---|---|---|
| `lockUnused` | `0 → 3`，写 `order_no` + `lock_time` | `id + member_id + coupon_status=0` | L49-61 |
| `markUsed` | `3 → 1`，写 `use_time` | `id + member_id + coupon_status=3 + order_no=` | L71-83 |
| `markUnused` | `3 → 0`，清 `order_no` + `lock_time` | 同上 | L94-106 |
| `selectStuckLocked` | 捞"锁太久"候选（含 `lock_time IS NULL`） | `coupon_status=3 AND (lock_time IS NULL OR < 阈值)` | L117-134 |
| `unlockStuck` | 对账专用 `3 → 0` | `id + coupon_status=3 + 时间阈值`（**不匹配 order_no**） | L149-158 |
| `selectCurrentById` | 当前读（`FOR SHARE`），CAS 失败后的兜底判断 | `id` | L186-200 |

- **三条 UPDATE 全部带 `member_id`**：会员 id 来自服务端上下文，带上它意味着"即使 `couponMemberId` 被写错成别人的券，也动不了别人的券"——**纵深防御，不是重复校验**（L35-37）。
- **`markUsed`/`markUnused` 都要求 `order_no` 相等**：幂等与防误伤都靠这个 `AND`（L28-32）。**`unlockStuck` 刻意不复用 `markUnused`**：历史遗留行可能 `order_no` 为空，等值匹配会永远解不开（L139-143）。
- **`markUnused` 刻意不清 `use_time`**：解锁只发生在状态 3 的券上（其 `use_time` 本来为 NULL）；写成"顺手置空"，一旦有人误用它处理已核销券就会静默抹掉核销痕迹（L88-90）。
- **`selectCurrentById` 为什么必须存在**：MySQL 默认 REPEATABLE READ，事务内普通 SELECT 读的是**快照**，"CAS 影响 0 行 → 再普通读一次做幂等判断"会读到过期快照，把并发同单的幂等命中误判成 409。`FOR SHARE` 是当前读（只加共享锁、读完即结束事务，不会成热点）。**⚠️ 只在事务内可用**（无事务会立刻释放锁），三处调用点都在 `@Transactional` 方法里（L160-178）。
- **⚠️ 列名显式写 camelCase 别名**：本服务 MyBatis 是手写装配，`map-underscore-to-camel-case` 没写在配置里；一旦它是默认 `false`，手写 SQL 返回的对象**全是 null**，兜底判断静默失效（BaseMapper 不受影响，它走 MP 自己的 resultMap）。别名把这个隐患变成不可能（L179-184）。

### 3.6 `service/impl/CouponMemberServiceImpl`（164 行）——会员侧读/领券
- `available(memberId)`（L50-82）：查 `status=0` 模板 → 过滤 `CouponRules.inValidWindow` → 组装 VO。`received` = "我在**任意状态**下领过这张模板"（L75-78），与表上 `uk_member_template` 一致：已用掉的券不能让"领取"按钮重新可点（点下去只会撞唯一键 → 409）。
- `receive(memberId, templateId)`（L86-122）**库存语义**：①模板不存在/停用 → 404「券不存在或已停发」，不在窗内 → 409「不在领取时间内」；②已领数 ≥ `max(1, perMemberLimit)` → 409「已达每人限领数量」；③`CouponMapper#increaseReceived`（`CouponMapper.java:26-28`）原子 +1，**已领满时影响 0 行** → 409「券已被领完」（"检查是否领完"与"记一次领取"压进同一条 SQL 才防得住超发）；④`insert` 撞唯一键 → catch `DuplicateKeyException` → `decreaseReceived` 抵消 +1 → 409「已领取过该券」。
  ⚠️ 第 ④ 步在当前事务边界下是"冗余但无害"的（紧随的异常会让整个事务回滚），**刻意保留**：将来有人把 +1 挪进独立事务/`REQUIRES_NEW` 时不至于静默丢掉补偿（L114-119）。
- `mine(memberId, status)`（L126-153）：过滤走 `CouponStatusProjection.dbStatusFilter`，响应走 `toExternal`；`expireOf`（L157-163）在 `validType=2` 时取 `now + validDays`（默认 7），否则取模板 `valid_end_time`。

### 3.7 `support/CouponRules`（86 行）与 `support/CouponStatusProjection`（102 行）

**`CouponRules`** 全部是**纯判断**（不查库、不抛异常；"哪一项不过抛哪条文案"留在 Service 里，因为**校验顺序本身就是契约**，L20-22）：
`enabled`（模板 `status==0`；注意极性：**0 才是可用**，`constant/CouponStatus.java:6-8`）、`inValidWindow`（`validType!=1` 恒 true）、`notExpired`、`meetsThreshold`（null 门槛 = 无门槛）、`usable`（前三者合取）、
`lockedBy(member, orderNo)`（**状态是 `LOCKED(3)` 且 `order_no` 就是本单**，两个条件缺一不可，L71-78）。
> ⚠️ **折扣计算不在 `CouponRules` 里**：取额与封顶在 `CouponQueryServiceImpl#discountFor`；`CouponRules` 只回答"能不能用"。

**`CouponStatusProjection`** —— **内外词表投影（C1 硬约束）**：库里 `0/1/2/3` → 对外仍是 `0/1/2`。

| 对外字段 | 规则 | 现状调用点 |
|---|---|---|
| `couponStatus` | 库里 `3(LOCKED)` → 对外 `1(USED)`，其余原样；`null` 按 0（列 NOT NULL，只为程序错误兜底） | `CouponMemberServiceImpl#mine`（L147）、`AdminCouponServiceImpl#records`（L164） |
| `?status=` 过滤 | `null`→不加条件；`0`→`[0]`；`1`→`[1,3]`；`2`→`[2]`；其它（含 `3`）→`[-1]`（**不可能命中的值**，而不是"忽略过滤"） | `CouponMemberServiceImpl#mine`（L128） |
| 可用券列表 | 只筛 `0`（**不变**）——锁定中的券不会出现在可用券里 | `CouponQueryServiceImpl#usableCoupons`（L88） |

**为什么必须有它**：前端两个工程已把 `0/1/2` 钉死，且旧实现里"下单瞬间券就已 USED"——锁定窗口内的券对外必须仍显示"已使用"，否则用户会第一次看到"未使用却不能用"的券（L10-13）。
**同一个投影服务两个端点**（`/api/coupon/mine` 与后台 `records`）：一处投影、一处不投影，同一张券会在两个页面显示成不同状态（`dto/CouponRecordVO.java:11-13`）。
⚠️ `?status=3` **不能**命中库里的 LOCKED（`3` 不在对外词表里，放进来等于对外暴露新状态，L76-80）。
⚠️ **`/internal/**` 端点不做投影**：trade 拿到的是库里真值 `0/1/2/3`；若 trade 要透传给前端，必须自己投影（L32-34）。测试 `CouponStatusProjectionTest`（11 例，含自洽断言）。

### 3.8 `service/impl/CouponQueryServiceImpl`（118 行）——试算与下单算钱
`discountFor(memberId, couponMemberId, goodsTotal)`（L46-79）：**校验顺序即契约**——`couponMemberId == null` → `0`（**正常路径，不是错误**）→ 非本人/不存在 400「优惠券不可用」→ 非 `UNUSED` 409「优惠券已被使用或失效」→ 单券过期 400「优惠券已过期」→ 模板停用 400「优惠券已停用」→ 模板窗口 400「优惠券已过期」→ 未达门槛 400「未满足优惠券使用门槛」。
最后 `Math.max(0L, Math.min(discount, goodsTotal))`：**封顶留在营销域**（券的业务规则，不是交易域的），否则"无门槛+大额券"会把 `pay_amount` 算成负数、污染订单/支付/退款三张表。
⚠️ 三态下第 3 步含义变宽：`1`/`2`/`3` 都落同一条 409（**文案不变**，用户在下单页看到的老提示就是这条）。
`usableCoupons`（L83-117）只筛 `coupon_status=0`——**三态之后这一行天然排除了 `LOCKED`**（L84-85），再按未过期 + 模板启用 + 门槛过滤。
唯一实现差异：`now` 取 `MallTime.now()`（Asia/Shanghai）而非 `LocalDateTime.now()`；差异只在"JVM 时区不是 +08:00"时出现，那时用默认时区会让券整体偏 8 小时（L31-35）。

### 3.10 `mq/OrderClosedConsumer`（129 行）+ `mq/OrderClosedMessage`（38 行）——关单兜底解锁
- 载荷 `OrderClosedMessage(orderNo, memberId, couponMemberId, reason, closedTime)` 是单体同名 record 的**契约副本**：字段名即 JSON 字段名，改一个就出现"事件到了但解不开"的死信（L8-11）；`reason` ∈ `CANCEL`/`TIMEOUT`/`ADMIN_CLOSE`，`couponMemberId == null` = 该单没用券。
- **ack 口径**（手动 ack）：正文解析不了 → 直接进死信 + `log.error` + ack；业务异常 → 投到**自己的**重试队列（带消息 TTL）或超限进死信，然后 **ack**；成功 → ack。⚠️ 无论哪条路径都必须 ack/reject 一次，否则消息一直 unacked 占着 prefetch 名额（L34）。
- **三道防线**（`OrderClosedMessage.java:14-21`）：①单体关单事务里同步 `unlock`；②本事件（事务提交后投递，覆盖同步调用失败/重启）；③每日对账（覆盖"事件也丢了"）。
- **⚠️ 不能从 `unlock` 的返回值判断"是不是我解的"**（L40-46）：`true` 既可能"本次真的改了"，也可能是"本来就已经是 UNUSED"（同步解锁已成功）；健康路径上必然是后者，把它写成"同步解锁没生效"的告警等于每次正常关单都报假警——**第一版就是这么写的，被证伪后改正**。
- **不需要按 `eventType` 过滤**：队列只绑 `order.closed` 一个路由键，"队列名 + 绑定就是过滤器"（L48-50）。

### 3.11 `task/CouponLockReconcileTask`（77 行）
`@Scheduled(cron = "${mall.marketing.reconcile-cron:0 5 0 * * ?}")`（L59），开关 `${mall.marketing.reconcile.enabled:true}`（L52-53），单轮上限 `${mall.marketing.reconcile-batch-size:200}`（L55-56）→ `unlockStuckLocks(batchSize)`。
两个刻意的写法：**cron 走配置**（验证时可用 `--mall.marketing.reconcile-cron="*/20 * * * * *"` 起服务实测它真的会跑；写死在注解里就只能等半夜）；**整个方法 try/catch + `log.error`**（定时任务抛异常会污染调度线程，后续轮次可能不再执行且没人会看到）。
存在理由（L13-24）：`unlock` 依赖调用方主动发起，而"MQ 丢事件 / 服务重启打断 / 人工改库 / 加 `lock_time` 列之前就锁着的行"这四种情况下**没有任何调用方会再来解它**——券会永远停在 `LOCKED(3)`，对外投影成"已使用"，用户既用不了也看不见。

### 3.12 `client/UserCenterMemberApi`（55 行）+ `client/UserCenterMemberClient`（117 行）——**唯一的跨域取数方式**
- `@HttpExchange(url="/internal/v1/user")` + `@PostExchange("/member/batch")`，返回**下游原始响应体** `ApiResponse<List<MemberBriefVO>>`（解包留给客户端类）。用声明式接口的收益（L15-28）：泛型不再靠人工传 `ParameterizedTypeReference`（原先容易把 `data` 反序列化成 `LinkedHashMap`，随后 `ClassCastException` 且**编译期看不出来**）、URL 只写一次、出站头不再手工写。
- 客户端类保留三件域语义（L30-40）：**连接装配**（`lb://` 走服务发现 + 超时；`http://` 直连排障，两者都挂同一个 `OutboundHeadersInterceptor` 注入 `X-Internal-Token`/`X-Trace-Id`，见 `config/LoadBalancedClientConfig.java:22-28`）、**错误语义**（传输失败/空响应 → `500`「系统繁忙，请稍后重试」；业务码非 0 → **原样透传** `BusinessException(code,message)`）、**入参形状**（空集合 → 空列表且**不发起调用**，L78-81）。
- 超时：连接 `300ms` / 读 `2500ms`（`UserCenterMemberClient.java:62-63`，`application.yaml:80-81` 同值）。⚠️ 注释给了理由：下游冷启动首调约 1.98s，照抄"目标值 300ms"会把正常请求判成故障（L46-47）。
- **为什么必须走契约**：`ums_member` 属会员域（`mall_user` 库），营销域没有访问权（L26-28）。测试用 `@MockitoBean UserCenterMemberClient` 断言"用户名/昵称被落进响应"（`InternalMarketingAdminCouponApiMySqlTest.java:48-49`）。

### 3.13 `config/GatewayIdentityResolver`（110 行）+ `config/WebConfig`（70 行）
本服务**不验签**，只判断"这个身份是不是网关给的"：常量时间比较 `X-Gateway-Auth`（`MessageDigest.isEqual`），通过后才信 `X-Member-Id`（L82-92）。
**fail-closed**：`mall.gateway.auth-token` 未配置 → 谁都不信，需要登录的接口全部 401（构造时只 WARN、不阻止启动，L52-56）。三条纪律：常量时间比较、未配置密钥=谁都不信、**不区分"没带头"与"带错头"**（对外都是 401「未登录」）。`resolveOrNull` 供限流切面回落 IP 用，`resolve` 抛 401。
`WebConfig` 注册两件事：`InternalApiAuthInterceptor` 只拦 `/internal/**`（L41-43）、`@MemberId Long` 解析器（L53-69）——**只支持 `Long`**：声明成基本类型 `long` 会解析不到而 500，绝不静默注入 0（那会让"归属校验"变成"归 0 号会员"，而它决定"能不能用别人的券"，L47-50）。
限流切面 `config/RateLimitAspect`（127 行）与参数解析**共用同一个 `GatewayIdentityResolver`**：两处各写一套"怎么算登录"会出现"参数解析认为是会员 A、限流记到 IP 桶"的静默不一致（L34-35）。⚠️ 顺序：Spring MVC **先解析参数、再调目标方法**，未登录请求在 `@MemberId` 处就抛 401，**早于**切面计数 ⇒ 匿名请求不占计数桶（L37-40）。

### 3.14 `config/RabbitMqConfig`（107 行）+ `support/MqTopology`（84 行）
- 交换机 `mall.oms.event`（topic、durable、非 auto-delete）由**发布方与每个消费方各自声明一次**：RabbitMQ 以第一次声明的参数为准，后到者参数有一点不同就 `PRECONDITION_FAILED`（经典事故，L16-21）。绑定不属声明参数，扇出正是靠"新增绑定"实现。
- 本服务自己的三条队列/三个路由键（**刻意不与单体 `event.*`、review `review.*`、user-center `notification.*` 同名**）：`mall.marketing.order-closed`（绑 `order.closed`）、`…retry`（绑 `marketing.retry`，死信回工作队列走 `marketing.redeliver`）、`…dlq`（绑 `marketing.dlq`）。**同名队列 = 竞争消费**，一条消息只被一个服务拿到 ⇒ "券偶尔没被兜底解锁"/"别人的业务少收一条事件"，现象随机、极难复现（`MqTopology.java:17-20`）。
- 重试队列**刻意用每条消息自己的 TTL** 而非队列级 `x-message-ttl`：队列参数一经声明不能改，会把"重试间隔"锁死在队列定义上（想调快就得删队列，L33-34）。
- 开关 `mall.mq.enabled`（默认 false）：false ⇒ 本配置类**整个不装配** ⇒ 完全不连 broker。⚠️ 这条**刻意不写进 `application-dev.yaml`**：profile 专属配置优先级高于测试的 `application.properties`，写在那里会让每个测试上下文都去连 broker（症状是"测试偶尔超时"，最难查的一类，L36-41）。

### 3.15 `mapper/CouponMapper`（34 行）+ `support/RequestValidator`（89 行）
`increaseReceived`/`decreaseReceived`：领券防超发/防重复的两条原子 SQL（见 §3.6）；换成"先 select 判断再 update"就会在并发下超发（L18-19）。
`RequestValidator#check`：跑 DTO 上的 Bean Validation，失败抛 `BusinessException(400, 原中文提示)`；报错顺序是契约的一部分——按 **DTO 字段声明顺序 → 同字段内"非空 → 长度 → 范围 → 格式"** 排序取第一条（L24-25、L44-50）。

## 8. 关键机制与不变量（承重墙）

| 不变量 | 落点（类:方法） | 违反会怎样 | 谁在守 |
|---|---|---|---|
| 券三态：`0 →(lock) 3 →(use) 1`、`3 →(unlock) 0` | `CouponMemberMapper#lockUnused/markUsed/markUnused` | 两态 ⇒ 下单不支付后券回不来（**旧实现的存量缺陷**：下单瞬间 `0→1`，全仓没有任何一处改回 0，库存回了、券没回） | `CouponTriStateMySqlTest`（含"解锁→再锁定"生命周期用例） |
| 并发下"只有一方拿到锁" | `lockUnused` 的 `coupon_status=0` 条件 + 影响行数 | 两个订单共用一张券（两单都抵扣） | `CouponTriStateMySqlTest`（8 线程：1 个 winner、7 个 409 且文案逐字） |
| 同单重复 `lock` 幂等（不报 409） | `CouponRules#lockedBy` + `selectCurrentById`（`FOR SHARE`） | 双击提交/重试被误判成 409 | 同上（8 线程同 orderNo 全部 true） |
| `lock_time` 与 `order_no` 原子同写 | `lockUnused`（同一条 UPDATE） | 出现"锁上了但没记时间/单号"的行 ⇒ 对账永远找不到它 | `CouponTriStateMySqlTest` `[lock] 首次锁定…` |
| 重复 `use` 不刷新 `use_time` | `markUsed` 影响 0 行时不执行 UPDATE | 核销时刻不可信，客服/对账查不出真实核销时间 | `[use 幂等]` 用例 |

## 9. 坑与已知边界（都能指到代码/注释）

1. **`lock` 里没有门槛校验（有意）**：契约没有 `goodsTotal`，门槛只能由先行的 `discount`/`usable` 判；两处都拦就是两套口径（`CouponCommandServiceImpl.java:37-41`）。
2. **两次读库不是 check-then-act 竞态**：读只决定文案，判定是 CAS；读错最坏是"文案不够精确"（同上 L43-46）。
3. **`selectCurrentById` 只能在事务内用**：`FOR SHARE` 无事务会立刻释放锁、退化成普通读（`CouponMemberMapper.java:176-177`）。
4. **手写 SQL 必须显式写 camelCase 别名**：`map-underscore-to-camel-case` 没写进配置，一旦为 `false`，兜底判断静默失效（本该幂等 true 的重复调用全变 409，L179-184）。
5. **`receive` 的 `decreaseReceived` 在当前事务边界下"冗余但无害"**：删掉它，将来把 +1 挪进独立事务时会静默丢掉补偿（`CouponMemberServiceImpl.java:114-119`）。
6. **模板 `valid_type=1` 且 `valid_end_time` 为 NULL 时领券会 500**：`expireOf` 取模板 `valid_end_time`，而 `sms_coupon_member.expire_time` 是 NOT NULL，MySQL 严格模式报 1406 → 对外 500「系统繁忙」。这是**单体既有行为**（同一份 `expireOf` 一字未改搬来），真实数据里"固定时间段"的模板必然有结束时间所以没被撞到过；`MarketingTestBase.java:166-172` 专门记录了这条边界。
7. **消费者不能从 `unlock` 返回值推断"谁解的"**：`true` 含"本来就是 UNUSED"的幂等命中，健康路径上必然是这种；第一版写的"同步解锁没生效"是假告警，已改正（`OrderClosedConsumer.java:40-46`）。
8. **`records` 的会员调用刻意不降级**（与 review 的昵称 fail-open 取向相反）：宁可报错，也不给出静默空用户名（`AdminCouponServiceImpl.java:44-48`）。
9. **`lock_time` 无索引**，对账查询走不了 `idx_member_status`（见 §4）。
10. **注释已过期一处**：`CouponStatusProjection.java:27-30` 写着"本批（P5-1）还没有任何公开端点调用它们"，实际现在 `mine`（L147）与 `records`（L164）都在用。
11. **`/internal/**` 不做投影**：trade 拿到库里真值 `0/1/2/3`，要透传给前端必须自己投影（`CouponStatusProjection.java:32-34`）。
12. **本服务无 springdoc/OpenAPI**（`pom.xml:17-18`）：对外契约靠"逐字相同 + 契约测试"守，新增端点不会自动进接口文档。
