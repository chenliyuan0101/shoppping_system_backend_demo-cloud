# `mall-product` 代码解析

> 一句话定位：商品域服务（SPU / SPU 详情 / SKU / 库存与库存流水 / 类目 / 品牌）——它持有 `pms_*` 六张表的**唯一写权**，
> 库存扣减与销量累加的知识在它这里（`ProductApplication` L7-12）；检索（ES）**不在它这**，它只"供给索引文档 + 委托检索 + 发布同步消息"。
> 范围：`src/main/java` 下 **81 个文件 / 5908 行**；测试 **17 个类（含 2 个支撑类 `AdminTokenMinter`/`ProductTestBase`，实际测试类 15 个）/ 3976 行 / 86 例 `@Test`**（`target/surefire-reports` 聚合同样是 15 类 86 例；口径见 §0 末的统计命令）。与其它文档的分工：本文讲"代码怎么组织、每个类怎么实现、改哪里会坏"；端口/路由表见 `系统说明.md`，一次请求的流转见 `系统流程与三大核心功能实现.md`。

## 2. 分层与包职责

- **`controller` / `internal`**：只做"参数 → Service 调用 → `ApiResponse.ok(...)`"，不放业务判断（唯一例外是 `#indexDocs` 的"三种取法只能给一种"，L151-158——那是**请求契约**）。
- **`service`（接口）+ `service.impl`**：接口定义跨域可见的契约形状；实现里放事务、缓存、降级、远程调用。`CodeStyleTest` L112 允许策略实现不叫 `*ServiceImpl`（两个检索实现即按能力命名）。
- **`client`**：出站装配。`CodeStyleTest` L81 限定本包只允许 `*Api`/`*Client`/`*Factory|*Interceptor`/客户端专属 `*Exception`。
- **`config`**：**组装根**在这里（而非 `app/`）——`WebConfig` 挂两个拦截器与 `@MemberId` 解析器、`MybatisPlusConfig` 以**窄包** `com.mall.product.mapper` 做 `@MapperScan`（L24，"误标 `@Mapper` 时立刻暴露"）、`RabbitMqConfig` 只声明交换机、`LoadBalancedClientConfig` 提供带 `OutboundHeadersInterceptor` 的 `@LoadBalanced RestClient.Builder`。
- **`domain` / `mapper`**：实体与 SQL。⚠️ `SpuMapper` 类注释 L16：**注解 SQL 不经过 MP 的 `@TableLogic`**，逻辑删除条件必须手写（`deleted = 0`）。
- **`support`**：无业务语义的工具与常量。`CodeStyleTest` L176/L166 钉住"`support`、`domain` 不得依赖入站/服务/客户端层"。
- **`mq`**：只放 `*Publisher`/`*Message`（`CodeStyleTest` L152）。

## 3. 核心类详解

### 3.1 `service/impl/StockCommandServiceImpl`（205 行）—— 库存/销量写契约（本服务最"承重"的类）

一句话职责：把改造前散在 `OrderServiceImpl`/`RefundServiceImpl` 里的库存扣减、回补、销量累加**原样搬进商品域**，一张表只由一个域改（类注释 L26-42）。

| 方法 | 做什么 | 关键行为 |
|---|---|---|
| `reserve(orderNo, lines)`（L55-78） | 预占（当前语义即实扣）+ 写流水 | 见下 ①②③ |
| `release(orderNo, lines, changeType)`（L80-118） | 回补 + 写对应类型流水 | 见下 ④⑤ |
| `incrementSales(orderNo, lines)`（L120-143） | SKU 与 SPU 的 `sales` 同时累加 | **无条件累加**（L130-137）：调用方必须已经在"待收货→已完成"的 CAS 抢到之后才调（L129 注释）；重复调用会重复累加 |
| `sortedBySkuId(lines)`（L146-153） | 按 `skuId` 升序 | 三个写方法的第一步 |
| `alreadyLogged(orderNo, changeType, skuId)`（L172-181） | 幂等判据 | `SELECT ... FOR UPDATE`（L180）；`orderNo` 空/空白 **不做**幂等收敛（L173-175） |
| `writeLog(...)`（L183-194） | 写 `pms_sku_stock_log` | `before_stock = after_stock - delta`（L191）；`remark` 与改造前逐字一致（L197-204：下单扣减/超时关单回补/退款回补/取消回补） |

**① 并发凭证 = 条件 UPDATE 的影响行数**（L64-71）：

```java
int affected = skuMapper.update(null, new LambdaUpdateWrapper<Sku>()
        .setSql("stock = stock - " + line.getQuantity())
        .eq(Sku::getId, line.getSkuId())
        .eq(Sku::getStatus, EnableStatus.ENABLED)
        .ge(Sku::getStock, line.getQuantity()));
if (affected == 0) { throw new BusinessException(409, "商品库存不足：" + spuTitleOf(line)); }
```
判定与扣减在数据库里原子完成，`affected == 0` 即库存不足；文案含商品标题（`spuTitleOf` L156-159 只在失败路径上查一次）。
`ConcurrentStockMySqlTest` 用 50 线程抢 13 件：恰好 13 成功、37 个 409（该类 L56 的 `@DisplayName`）。

**② 防死锁 = 按 `skuId` 升序**（L58、L83、L123 + L146-153）：多 SKU 订单在同一事务里多次更新 `pms_sku` 时加锁顺序一致，不会与其它订单交叉加锁。

**③ 流水 before/after 取"更新后再读"**（L73-75）：同事务内能读到刚写入的值；若"先读后更新"，并发下会写出与相邻流水对不上的账。

**④ 回补时绕过逻辑删除判断 SKU 存在**（L99-105）：后台改商品会把旧 SKU 逻辑删除，直接 `selectById` 得到 null 就跳过会让历史订单的库存**静默不回补**。
所以走 `skuMapper.selectByIdIgnoreLogicDelete`（`SkuMapper` L38-40 的原生 SQL），行真没了才 `log.warn("回补库存时 SKU 已不存在(需人工核对)...")`（L102-103）。

**⑤ 幂等闸（P6-5 #2）**：同一 `(orderNo, changeType, skuId)` 只回补一次（L94-98 跳过并记 info 日志）。
两层防护：①应用层判据 `alreadyLogged` 用 `SELECT ... FOR UPDATE`——**行不存在时取间隙锁**把并发同键调用串起来；②`pms_sku_stock_log` 上的唯一索引 `uk_order_type_sku`（`V1__baseline.sql` L76）作最后一道防线，万一判据被绕过直接报 1062 而**不是静默多回补**（`db/04-uk-order-type-sku.sql` L18-22）。
⚠️ 已知影响面（`ReleaseIdempotencyMySqlTest` L142 断言）：同键**并发**时兜底是"让后来者失败"（死锁/1062 → 事务回滚、HTTP 仍 200），且该唯一索引对 `reserve` 的重复并发扣减同样生效。

**⑥ 索引同步与时序**：三个方法末尾都调 `productSearchService.markDirty(...)`（L77、L117、L142）——库存/销量是索引字段（`totalStock`/`sales` 排序），
调用方**在事务内**调它，所以"提交后才投递"由 `ProductSyncPublisher` 兜住（见 3.7）。
回补**不在**调用方（`mall-trade`）的事务里执行：trade 侧 `StockReleaseAfterCommit.release`（`mall-trade` L63-80）"有活跃同步就注册 `afterCommit`，没有就立刻执行"，
本地 CAS 先提交 ⇒ 重试被 CAS 挡住 ⇒ 双回补在结构上不可能；本服务这一侧的对应防线就是 ⑤ 的幂等闸 + 唯一索引（**重复调用本身也无副作用**）。

### 3.2 `service/impl/ProductPortalServiceImpl`（269 行）—— 门户读路径（缓存 / ES / MySQL 三岔口）

**TTL 常量**（L60-68）：类目树与品牌 30 分钟、货架分页 **45 秒**、商品详情 5 分钟；`MAX_PAGE_SIZE = 50`（L60）。

| 方法 | 关键行为 |
|---|---|
| `enabledCategoryTree()`（L85-99） | 读 `mall:cache:category:tree` → 未命中查"仅 `status=1`"的类目、`CategoryTreeBuilder.build` 组两级树、回填 30min |
| `enabledBrands()`（L103-114） | 同构：`mall:cache:brand:list` + `BrandSupport.enabledBrands` |
| `pageOnShelf(...)`（L120-164） | 页码/页宽先收敛（`PageKit.page` + `min(50, max(1,pageSize))`，L123-124）→ 算 key → 命中即返回 → **有 keyword 走 ES、否则 MySQL** |
| `detailOnShelf(spuId)`（L199-248） | 命中缓存也**必须回读 DB**（见下） |
| `shelfVersion()`（L257-268） | 读 `mall:cache:product:ver`，缺失/非数字 → 0 |

**货架缓存键**（L126-129 + `CacheKeys#productShelf` L53-55）：
`mall:cache:product:shelf:v{version}:{sha256(全部筛选参数的 "|" 拼接) 前 16 字节 hex}`——版本号 + 参数摘要，让"后台任意写操作"用一个 `INCR` 让**全部**旧 key 立即失效，无需遍历删除。
缓存写入点有两处：空结果也写（L155-158）、正常结果写（L162），TTL 都是 `SHELF_TTL`(45s)。

**有 keyword 走 ES 否则 MySQL**（L145-150）：`if (StringUtils.hasText(keyword)) { PageResult<...> esResult = searchByEs(...); if (esResult != null) return esResult; }`
`searchByEs`（L171-188）的结构是"**只有异常才回落**"：`try { ...; return result; } catch (Exception e) { log.warn("ES 检索失败，降级为 MySQL LIKE：keyword={} err={}", ...); return null; }`
`null` ⇒ 继续走下面的 `spuMapper.countShelf` / `pageShelf`（L152-163）。**一次请求有且仅有一条 WARN**——所以远程实现自己不记 WARN（见 3.4）。
ES 路径拿到的 spuId 要回表装配，并用 `orderByGivenIds`（L191-195）按 ES 给的顺序重排（`selectBatchIds` 不保证顺序），MySQL 里已删除的自动被过滤掉（`filter(Objects::nonNull)`）。

**详情缓存**（L199-213）：命中 `mall:cache:product:detail:{spuId}` 后**仍以 DB 为准**——
回读 SPU 判断上下架（不是 1 → 删缓存 + `BusinessException(404, "商品不存在或已下架")`），并回填 `sales` 与 `liveSkus(spuId)`（L251-255 实时读在架 SKU 的价格/库存）。
**库存绝不走缓存**（L204 注释）。

| `updateProduct`（L263-280） | **SKU 全量重建**（L275-277）：先按 `skuCode` 读出旧行（含逻辑删除行）继承 `image`/`sales`，再 `delete` 全部旧行后逐条 `insert` |

| `deleteProduct`（L299-310） | 逻辑删除 SPU + 其 SKU → 同步一次移出索引（L309） |
| `updateBrand`（L350-377） | 品牌改名才触发（L373）：`syncBrandLater(id)` 重写该品牌下在架商品的索引文档（`brandName` 是索引字段） |
| `evictPortalCache(spuId)`（L402-412） | 删首页/类目树/品牌列表/该 spu 详情 4 个固定 key + `INCR mall:cache:product:ver` |

**为什么索引同步必须在 `afterCommit`（P6-4 实测出来的真缺陷，注释 L414-431 记着全过程）**：后台逻辑删除 → 行内调 `syncLater` → `mall-search` **回读 product 的库**组装文档；
若回读发生在本地事务**提交之前**，读到的是"还没删"的状态 ⇒ 把文档保住/写回索引 ⇒ **已删除的商品仍能被搜到**（点进去详情 404）。实测 `_id=22136` 留在索引里、`index-docs` 对它返回 `docs:[]`、`mall:es:pending` 为空、第 1 次复现没留幽灵第 2 次留了 ⇒ 间歇性竞态。
**缓存失效原本就走 afterCommit，只有索引同步漏了** ⇒ P6-5 统一为 `TxCallbacks` 单一实现（`mall-common/support/TxCallbacks` L40-66：有活跃同步就注册 `afterCommit`；无事务**或提交阶段已开始**就立刻执行；只挂 `afterCommit`、不挂 `afterCompletion`）。回归闸门：`AdminIndexSyncAfterCommitMySqlTest`（3 例）。

### 3.4 `service/impl/RemoteProductSearchService`（340 行）—— 检索委托（唯一会"抛"的实现）

### 3.7 `mq/ProductSyncPublisher` + `mq/ProductSyncMessage` —— 索引同步的发布方

- **拓扑**（`MqTopology` L39-43）：交换机 `mall.pms.sync`（direct）、队列 `mall.pms.es-sync`（本服务**不声明**）、路由键 `product.sync`。

### 3.8 `client/SearchProductsApi`（80 行）+ `client/SearchProductsClient`（191 行）—— 出站边界

- `SearchProductsApi` 是 Spring HTTP Interface 声明式接口（`@HttpExchange("/internal/v1/search")` L46），**7 个方法**：`POST /products`（L50-51）、`POST /reindex`（L54-55）、`GET /status`（L58-59）、`POST /sync/{spuId}`（L62-63）、`DELETE /product/{spuId}`（L66-67）、`POST /sync-by-brand/{brandId}`（L70-71）、`GET /product/{spuId}`（L78-79）。返回类型是**下游原始响应体** `ApiResponse<T>`——**不判业务码**（`code != 0` 要原样返回给调用方，好与传输失败区分）。
- `SearchProductsClient` 只保留域语义三件事（类注释 L27-38）：连接装配、错误语义、数据形状适配。连接（构造器 L65-76）：`mall.search.base-url` 默认 `lb://mall-search`（非 `lb://` 前缀则直连）、超时 **`connect-timeout-ms=300` / `read-timeout-ms=2500`**（L67-69，照 P2 实测口径：下游冷启动首调 1.98s，抄"目标值 300ms"会把正常请求判成故障）。出站头由 builder 上的 `OutboundHeadersInterceptor` 统一注入，接口方法不写 `.header(...)`。

### 3.10 `config/InternalApiAuthInterceptor`（63 行）+ `AdminAuthInterceptor`/`JwtVerifier` —— 入站鉴权

- **内部闸**：头名 `X-Internal-Token`（L46），密钥 `mall.internal.token`（L50）。**fail-closed**：未配置 ⇒ `BusinessException(403, "内部接口未配置访问凭据")`（L57-59）；不匹配 ⇒ `403 "内部接口鉴权失败"`（L61-63）；比较用 `MessageDigest.isEqual`（L68-70）做**常量时间**比较。类注释 L21-33 说明"为什么必须有这道闸"：`/internal/v1/stock/**` 能改商品真值，暴露且无鉴权 = 任何人可把库存扣到 0 / 凭空回补 / 刷高销量。
- **管理端闸**（`AdminAuthInterceptor` L49-58）：`AuthHeader.bearer(...)`（`AuthHeader` L25-33，`Bearer ` 前缀**大小写敏感**，缺/格式错 → 401「未登录」）→ `JwtVerifier.parse` → `typ` 必须 `admin`（否则 401「登录已失效，请使用管理员账号登录」）。
- **验签器**（`JwtVerifier` L42-165）：纯 JDK HS256，`exp < now` 即失效（**无时钟宽容窗口**），签名比对同样常量时间；`mall.jwt.secret` **缺失或短于 32 位直接拒绝启动**（L68-75）；**没有 `createToken`**（只验签不签发）；`mall.jwt.expire-hours` 读出来只打日志、**不参与校验**（L56-64）。
- **`GatewayIdentityResolver`**（99 行）：读网关注入的 `X-Gateway-Auth` 比对 `mall.gateway.auth-token`（常量时间），相等才信 `X-Member-Id`；未配置密钥 ⇒ **谁都不信**（`resolveOrNull` L78-80 返回 null），对外统一 401「未登录」（L68-74）。**当前无端点使用**。

`ProductQueryServiceImpl` 刻意保持"薄"（类注释 L24-28）：只读自己的表 + 转契约快照，不放业务规则、不改状态。`skus/spus` 为**批量**形状（L57-85，避免列表页逐行远程调用）；`minEnabledSkuPrices`（L89-100）取 `status=1` 且价格非空的最低值，**没有可用 SKU 的 SPU 不出现在结果里**；`homeFeed(size)`（L104-113）做三次门户读的装配，`size` 非法（≤0 或 >50）回落默认 8（L35-38、L105）。

### 3.12 `support/RequestValidator`（96 行）+ `support/GlobalExceptionHandler`（78 行）—— 校验与错误形状

`RequestValidator.check(target)`（L41-49）：把 DTO 上的 Bean Validation 约束跑一遍，失败抛 `BusinessException(400, 原中文提示)`。理由（类注释 L18-22）：接口约定是"HTTP 恒 200 + 业务 code"，而 `@Valid` 抛的异常**只在 Controller 层被拦截**，Service 层（内部调用/测试）不生效 ⇒ 约束写在 DTO 上、由 Service 调 `check` 触发，两条路径结果一致；报错顺序按 ①字段声明顺序 → ②同字段内注解优先级（非空→长度→范围→格式）取第一条（L51-95）。
`GlobalExceptionHandler`：`BusinessException → code`（L26-29）、`MethodArgumentNotValid → 400`（L40-48）、`HttpMessageNotReadable → 400「请求体格式不正确」`（L56-60，注释说明以前会落到 500「系统繁忙」而误导排查）、`IllegalArgumentException → 400`、`NoResourceFound → 404`、兜底 `Exception → 500「系统繁忙，请稍后重试」`（L73-77）。

## 6. 定时任务与异步

**定时任务：无。** 模块内 `@Scheduled` / `@EnableScheduling` 一处都没有（grep 全模块仅命中 `ProductApplication` L25-29 的注释，说明"本批没有定时任务，`ProductSearchSyncTask` 属 mall-search"）。⚠️ 该注释同时记着一条真坑：`@Scheduled` 在缺 `@EnableScheduling` 时**永远不会执行而且不报错**（"代码写了、任务不跑"的假绿）。

异步只有两条，都挂在事务同步上：

| 机制 | 触发点 | 做什么 | 与谁幂等 |
|---|---|---|---|
| `TxCallbacks.afterCommitOrNow`（`mall-common/support/TxCallbacks` L40-66） | 后台写路径 5 处（`AdminProductServiceImpl` L259/279/296/309/375）+ 缓存失效 L407 + `ProductSyncPublisher` 的 3 个入口 | 把"缓存失效/索引同步/MQ 投递/兜底同步"推迟到**提交后**；无事务或提交阶段已开始 ⇒ 立刻执行 | 不幂等（是时点保证，不是去重）；靠 ①库存幂等闸 ②MQ 消费方重试语义 |
| MQ 投递（RabbitMQ 异步） | 同上 | 库存/销量/后台写变化 → 通知 search 重算索引 | 消费方按 spuId upsert（幂等）；本服务只发首投 |

## 9. 坑与已知边界（只写代码里能指到的）

**注释与代码已经不一致的地方（读注释时注意）**：

1. `GatewayIdentityResolver` 类注释 L35-40 写"**本服务对 `/api/admin/**` 不做自己的鉴权**是一个已知边界"——**已过期**：`AdminAuthInterceptor`（P6-1b）+ `WebConfig` L63-64 已装上验签闸；同一条注释里的"本批的 **21 个端点**"也对不上（它自己列的 4+16+7=27，代码里实际是**对外 20 + 内部 10**）。
2. `ProductTestBase` L249 与 `PortalCacheMySqlTest` L124 的注释引用 `AdminProductServiceImpl#evictOnCommit`——**该类里没有这个方法**，实际方法是 `evictPortalCache`（L402）。
3. `ProductSearchService#markDirty` 的接口注释（L52）把 MQ 通道写成队列名 `mall.pms.es-sync`；实际投递落点是**交换机** `mall.pms.sync`（`MqTopology` L39-41）——别读成"直接投队列"。

**fail-open / fail-closed 的取舍**：

| 判据 | 失败时行为 | 依据 |
|---|---|---|
| Redis 不可用（读缓存 / 写待同步集合） | **fail-open**：读返回 null 回落 DB、`SADD` 返回 -1 只 warn，不抛 | `CacheService` L59-70、L183-195；`SearchUnavailableProductSearchService#markPending` L288-291 |
| 索引同步/写/删失败 | **fail-open**：不阻塞商品写 | `RemoteProductSearchService` L207-250 |
| `reindex` 失败 | **抛** `BusinessException(500)` / 透传下游码 | 运维端点，静默失败没意义（L187-201） |
| 检索（关键字）失败 | **抛** `IllegalStateException` → 调用方回落 MySQL LIKE | "只有异常才回落"的分支结构（L171-188） |
| 内部令牌未配置/不匹配、网关身份凭据未配置 | **fail-closed**：403 / 401 | 这两条路径能改商品真值 / 能决定身份 |

**已知遗留面（代码注释里明确记着的）**：

- **管理端鉴权不完整**（`AdminAuthInterceptor` L24-36、`WebConfig` L38-41）：一个"签名正确、没过期、`typ=admin`，但账号已被禁用/已登出"的令牌在 P7 之前仍能通过；`ver` **读出来但不校验**。
- **`@MemberId` 解析器无使用方**（`WebConfig` L42、`GatewayIdentityResolver` L35-38）：本服务没有任何会员侧端点。
- **SKU "全量重建"换主键**（`AdminProductServiceImpl` L492-502）：历史订单的 `sku_id` 无法保留——简化模型的已知代价；库存回补侧已改为绕过逻辑删除读取 SKU（§8）。
- **`uk_order_type_sku` 带来的一处行为变化**（`db/04-uk-order-type-sku.sql` L18-22）：同键**并发**时从"静默多扣/多补"变成"报错回滚"（安全方向，但确属行为变化）；`reserve` 的重复并发扣减也受该索引影响。
- **`findById` / `searchByTitle` 的语义边界**（`RemoteProductSearchService` L307-339）：`code=0,data=null` 是"索引里确实没有"，读不到则**抛**；`searchByTitle` 未实现（缺的是 search 侧"按标题取文档"端点，且本方法无生产调用方，不为它造 N+1 通道）。
- **`drainPending` 刻意返回空**（`SearchUnavailableProductSearchService` L268-278）：`mall:es:pending` 的真消费者是别人，顺手取走等于偷任务。
- **无定时任务、无 `@EnableScheduling`**（`ProductApplication` L25-29）：将来把兜底任务搬进来时必须同时加注解，否则"代码写了、任务不跑"且不报错。
