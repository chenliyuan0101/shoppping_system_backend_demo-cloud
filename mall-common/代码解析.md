## 1. 请求入口（对外 + 内部）

**没有端点。** 它是库：无 `main`、无 `@SpringBootApplication`、**无端口**、**无 `spring.application.name`**、**无 DB schema**、**无 `application*.yaml`**（`src/main/resources` 下只有那一个 imports 文件）。也没有 `/internal/v1/**` 端点——那些是各领域服务的，校验在各自的 `InternalApiAuthInterceptor`（§5.2）。所以本节给的是"它被使用的三种形态"：

| 形态 | 落点 | 谁在用 |
|---|---|---|
| 自动装配清单 | `...AutoConfiguration.imports:1` | 8 个服务启动时 Boot 读取 ⇒ 调 `MallCommonAutoConfiguration` 注册 3 个 Bean |
| 被注入的 Bean | `OutboundRestClientFactory`（14 个客户端构造器注入）、`CacheService`（20 处主代码注入）、`FilterRegistrationBean<TraceIdFilter>` | 各服务的 `client/`、`support/`、`config/` |
| 静态工具/常量/注解 | `JsonKit`、`PageKit`、`MallTime`、`TxCallbacks`、`YesNo`、`GatewayAuthHeaders`、`AuthAttribute`、`MemberId` | 直接 `import` 调用（无 Bean、无生命周期） |

- 唯一"看起来像端点"的是 `TraceIdFilter` 的 URL 映射 `/*`（`MallCommonAutoConfiguration.java:68`）——过滤器，不是端点。
- 网关**不依赖**本模块（`mall-gateway/pom.xml` 无 `mall-common` 依赖）：网关的错误响应体是手写字符串，traceId 过滤器也自成一份（见 `mall-gateway/网关代码解析.md` §2.3）。

## 2. 分层与包职责

| 包 | 放什么 | **不放**什么 | 约束 |
|---|---|---|---|
| `client/` | "怎么装配一个 RestClient" + "该带哪些头" | 域语义（路径/超时/错误语义在各服务 `*Client`/`*Api`）、重试、熔断、日志埋点 | `OutboundHeadersInterceptor.java:35-36`："只干补齐两个头这一件事" |
| `web/` | 入站边界里唯一与业务无关的一环：traceId → MDC | 鉴权（身份头校验在各服务的 `GatewayIdentityResolver`/`InternalApiAuthInterceptor`） | 只能有一个 servlet 过滤器 |
| `support/` | 无状态工具 + 唯一持有外部连接的 Redis 门面 | 域内 Redis key（`CacheKeys` 各服务自持）、域内 MQ 拓扑（`MqTopology`/`MqMessages` 各服务自持） | `CacheService` 是唯一带降级语义的类 |
| `constant/` | 只有 `YesNo` | 领域枚举、状态码、错误码 | 错误码属契约面（§9.2） |
| `autoconfig/` | **唯一的组装根** | 组件扫描式的 `@Component`/`@Service`（会被扫不到） | 见下 |

**组装根为什么在这里、而不是各服务扫包**（`MallCommonAutoConfiguration.java:18-22`）：8 个服务的 `@SpringBootApplication` 只扫自己的 `com.mall.<域>` 包（刻意：扫描面越小启动越可预测）⇒ 共享内核里的类一旦用 `@Component` 就永远不会被扫到。因此三个需要成为 Bean 的类**去掉了 `@Component`/`@Service`/`@Order`**，改由自动装配显式声明、登记在 imports 清单；注册方式集中在**一处**，各服务零改动。

⚠️ **唯一例外：`@LoadBalanced RestClient.Builder` 仍留在各服务**（8 处：7 个 `config/LoadBalancedClientConfig.java` + trade 的 `app/OutboundClientConfig.java:27-33`）。因为 `@LoadBalanced` 必须标在**使用方**的 `@Bean` 方法上（`LoadBalancerBeanPostProcessor` 认的是 bean 定义上的注解；只写在注入点上会变成"按限定符找不存在的 bean"⇒ 启动失败，实测记录在 `mall-product/config/LoadBalancedClientConfig.java:16-19`）。共享内核只能把它当**参数**接进来（`OutboundRestClientFactory#build` 的第一个参数）。

## 3. 核心类详解（13 个类全列）

### 3.1 `client/OutboundHeadersInterceptor`（72 行）

一句话：给**所有出站请求**补两个头——`X-Internal-Token`（覆盖式写）与 `X-Trace-Id`（有值才写）。

`intercept(HttpRequest, byte[], ClientHttpRequestExecution)` → `:60-71`：
```java
if (internalToken != null && !internalToken.isBlank()) {
    request.getHeaders().set(HEADER_INTERNAL_TOKEN, internalToken);   // set，不是 add
}
String traceId = MDC.get(MDC_TRACE_ID);
if (traceId != null && !traceId.isBlank()) {
    request.getHeaders().set(HEADER_TRACE_ID, traceId);
}
return execution.execute(request, body);
```
四个刻意的取舍（类注释 `:26-37`）：①**`set` 而不是 `add`** ⇒ 调用点即使手工写了同一个头，下游也**只看到一个值**（不会出现"两个 `X-Internal-Token`"的歧义），这也让"逐步去掉手工写法"可以分批进行；②**traceId 只在 MDC 有值时透传** ⇒ 定时任务/MQ 消费者线程没有 MDC 时**不编造** id（宁可"没有关联"，也不要"关联到一个假 id"）；③**密钥为空串时不写这个头**（`:63`）并在构造器 warn（`:52-58`）；④**不做重试/熔断/埋点**——那些各自有归属。

| 常量 | 值 | 行 | 谁必须与它逐字一致 |
|---|---|---|---|
| `HEADER_INTERNAL_TOKEN` | `X-Internal-Token` | `:44` | 7 个服务的 `InternalApiAuthInterceptor.HEADER_INTERNAL_TOKEN`（各自又声明一遍，如 `mall-product/.../InternalApiAuthInterceptor.java:46`）+ 8 个服务测试基类的 `TOKEN_HEADER` |
| `HEADER_TRACE_ID` | `X-Trace-Id` | `:46` | 网关 `support/TraceIdFilter`、本模块 `web/TraceIdFilter.TRACE_ID_HEADER` |
| `MDC_TRACE_ID`（private） | `traceId` | `:48` | 本模块 `TraceIdFilter.MDC_KEY`、各服务 `logging.pattern.level` 的 `%X{traceId:-}` |

⚠️ MDC 键是**私有字面量**（`:48`），没有引用 `TraceIdFilter.MDC_KEY`——靠"逐字一致"维系，改一处不会有编译错误（§9.1）。

挂载点（谁 `new` 它）：8 个服务各一处，如 `mall-product/src/main/java/com/mall/product/config/LoadBalancedClientConfig.java:24-30`（`@Bean @LoadBalanced RestClient.Builder` + `.requestInterceptor(new OutboundHeadersInterceptor(internalToken))`）、trade 的 `mall-trade/src/main/java/com/mall/trade/app/OutboundClientConfig.java:27-33`。历史背景（`:18-19`）：该头原先在**全项目 42 处**调用点手工 `.header(...)`，漏一处就是"本地跑得通、换服务就 401"。覆盖它的测试：`mall-user-center/.../client/ProductSnapshotClientTest.java:96`。

### 3.2 `client/OutboundRestClientFactory`（53 行）

一句话：一个方法代替原先 14 份"连接装配"样板。`build(RestClient.Builder loadBalancedBuilder, String baseUrl, long connectTimeoutMs, long readTimeoutMs)` → `:43-52`：
```java
RestClient.Builder builder = baseUrl.startsWith("lb://")
        ? loadBalancedBuilder
        : RestClient.builder().requestInterceptor(new OutboundHeadersInterceptor(internalToken));
SimpleClientHttpRequestFactory requestFactory = new SimpleClientHttpRequestFactory();
requestFactory.setConnectTimeout(Duration.ofMillis(connectTimeoutMs));
requestFactory.setReadTimeout(Duration.ofMillis(readTimeoutMs));
return builder.baseUrl(baseUrl).requestFactory(requestFactory).build();
```
- **两条分支的头处理刻意不同**（`:18-24`）：`lb://` 用注入的 `@LoadBalanced` builder（它上面**已经**挂了拦截器，不再加第二个）；`http://` 直连用普通 builder + **显式加同一个拦截器**。
- **这是修掉"直连丢内部令牌头"的关键**（`:13-17`）：直连分支原先用普通 `RestClient.builder()`，不带令牌头；真库桩测试就是走直连，一漏就被断言抓到，原文 `Expecting actual: [null] to contain "test-internal-token"`。现在"直连排障模式"与"生产模式"发出的头完全一致 ⇒ 排障时不会因为少一个头而得到 401、把问题指向错误方向。
- **超时不设默认值**：由调用方按域传（javadoc `:40`："关键路径上的域各有各的值，别统一成一个"）。已核两处：`product/SearchProductsClient.java:67-70` = 300/2500ms、`user-center/ProductSnapshotClient.java:76-79` = 300/2000ms。
- 直连分支的触发方式：覆盖 base-url（如 `mall-product/.../application-prod.yaml:66` `${MALL_SEARCH_BASE_URL:lb://mall-search}` 传 `http://host:port`），以及**不启 Spring 的线格式契约测试**——`user-center/ProductSnapshotClient.java:100-104` 的兼容构造器 `this(builder, new OutboundRestClientFactory(internalToken), ...)`（注释明写"这正是'直连也要带 `X-Internal-Token`'的保证，也是这个重载存在的唯一理由"）。
- 不变量：**任何出站客户端都必须经由本方法装配**，绕开它直接 `RestClient.builder()` 就等于回到"手工写头"的老路。测试：`ProductSnapshotClientTest`（4 例，桩服务器 `http://127.0.0.1:{port}`）、`mall-product/.../SearchRemoteIntegrationTest`、`mall-review/.../MemberSnapshotClientTest`。

⚠️ **坑**：构造器参数上的 `@Value("${mall.internal.token:}")`（`:30-33`）在自动装配路径**不被解析**——装配走 `MallCommonAutoConfiguration.java:46-49` 里 `@Bean` 方法参数上的 `@Value`；全仓只有两个兼容构造器 `new` 它，所以该注解当前是**装饰性**的（§9.1）。

### 3.3 `web/TraceIdFilter`（65 行，servlet 版）

一句话：把网关给的 `X-Trace-Id` 放进 MDC，让本服务**每一行日志**都带上它。`doFilterInternal(...)` → `:51-64`：
```java
String incoming = request.getHeader(TRACE_ID_HEADER);
String traceId = (incoming != null && SAFE.matcher(incoming).matches())
        ? incoming
        : UUID.randomUUID().toString().replace("-", "").substring(0, 16);
MDC.put(MDC_KEY, traceId);
try { chain.doFilter(request, response); } finally { MDC.remove(MDC_KEY); }
```
常量：`TRACE_ID_HEADER = "X-Trace-Id"`（`:45`）、`MDC_KEY = "traceId"`（`:47`）、私有 `SAFE = ^[A-Za-z0-9_-]{8,64}$`（`:49`）。三个刻意之处（类注释 `:25-33`）：
①**没有头时自己生成**（`:57`，UUID 去 `-` 取前 16 位）——服务会被直接调用（本机排障、真库套件、内部探针），那种路径也应有 traceId；②**形状闸门**——直连时客户端可以直接塞头，不校验等于允许把换行写进日志（**日志注入**）⇒ 不合规丢弃重生成；③**用完必清 MDC（`finally`）**——Tomcat 线程是复用的，不清就会把上一个请求的 id 留给下一个（"日志里 traceId 张冠李戴"比没有 traceId 更难查）。

注册方式（**不在类上挂 `@Order`**）：`MallCommonAutoConfiguration.java:64-72` 用 `FilterRegistrationBean<TraceIdFilter>`——`addUrlPatterns("/*")`、`setOrder(Ordered.HIGHEST_PRECEDENCE)`、`setName("traceIdFilter")`。顺序必须早于所有其它过滤器/拦截器，**连"鉴权失败"那条日志也带得上 id**（排查时最需要的往往正是它）；用显式注册也避免"类上注解 + 装配类"两处都能改顺序的歧义（`:58-63`）。
与配置配对：8 个服务的 `application.yaml` 都有 `logging.pattern.level: "%5p [%X{traceId:-}]"`（如 `mall-product/.../application.yaml:88-90`）；`:-` = 取不到就留空，定时任务/MQ 线程没有 traceId 是刻意的、别当 bug。
覆盖它的测试：`mall-trade/src/test/java/com/mall/trade/common/TraceIdFilterTest.java`（**5 例**：合规值原样进 MDC、缺失则生成 16 位 hex、五种非法形状丢弃重生成、正常路径清 MDC、**异常路径也清 MDC**）。⚠️ 类内 `log` 字段（`:42`）没有任何调用。

### 3.4 `support/CacheService`（263 行）——本模块最长、最需要小心的类

一句话：Redis 的**唯一出口**，且**永不把 Redis 故障变成业务故障**（fail-open）。

| 方法 | 语义 | Redis 不可用时 | 行 |
|---|---|---|---|

| `get(String)` | 取字符串 | `null`（回落 DB） | `:59-70` |

### 3.6 `support/TxCallbacks`（67 行）

一句话："事务提交后再执行"——让跨服务副作用（写缓存、bump 版本、发索引同步）不会在回滚后仍然生效。`afterCommitOrNow(Runnable)` → `:40-66`：
```java

});
```
- **只挂 `afterCommit`，不挂 `afterCompletion`**（`:24`）：挂后者会在回滚时也执行。

## 9. 坑与已知边界

### 9.1 库自身的坑（都能指到代码）

1. **`OutboundRestClientFactory` 构造器上的 `@Value` 是装饰性的**：`:30-33` 标了 `@Value("${mall.internal.token:}")`，但装配走 `MallCommonAutoConfiguration.java:46-49` 的 `@Bean` 方法参数 ⇒ 该注解不被解析；全仓只有两个兼容构造器 `new` 它（`user-center ProductSnapshotClient.java:102`、`review MemberSnapshotClient.java:89`）。别靠它取配置。
2. **MDC 键在两处各写了一遍字面量**：`OutboundHeadersInterceptor.java:48`（private `MDC_TRACE_ID = "traceId"`）与 `TraceIdFilter.java:47`（public `MDC_KEY = "traceId"`），后者**没有被前者引用**。改一处不会有编译错误，只会让"出站透传的 traceId"与"日志里的 traceId"变成两个不相干的东西。
3. **`X-Internal-Token` 的头名常量有 8 份**：本模块 1 份（`:44`）+ 7 个服务的 `InternalApiAuthInterceptor` 各 1 份。v5.2 只上移了"出站写头"那一份，**没有**收敛入站校验侧的常量 ⇒ 改头名要改 8 处 + 各服务测试基类的 `TOKEN_HEADER`。
4. **`TraceIdFilter` 的 `log` 字段未被使用**（`:42`）：类内没有任何日志调用；为"显式 SLF4J 形态"保留，不是笔误，但会被 IDE 报 unused。
5. **`TxCallbacksTest` 的注释与实现口径不一致**：`mall-product/.../TxCallbacksTest.java:38-42` 说"阶段标记就是靠 `afterCompletion` 清的"，而实现是在 `afterCommit` 的 `finally` 里清（`TxCallbacks.java:56-63`），且**没有**覆写 `afterCompletion`；测试之所以绿，是因为 `@AfterEach` 走完生命周期在前、用例断言在后。改 `TxCallbacks` 时不要照该注释行事。
6. **`setIfAbsent(key, value, null)` 会得到 5 分钟默认 TTL**（`:164`）：这个隐式窗口"看起来合理但没人知道"；唯一调用方（trade `IdempotencyGuard.java:53`）传的是自己的锁 TTL。
7. **`getJson` 反序列化失败会删 key**（`:103`、`:118`）：既是自愈也是**静默失效**——类型不兼容的旧值（如改造前单体的老形状）会被清掉、下次回源 DB；日志级别只有 WARN。
8. **本模块没有自有测试**：这个库的行为只由各服务的测试**间接**守。改它的最小验证集 = `mall-trade TraceIdFilterTest` + `mall-product TxCallbacksTest` + `mall-trade RedisFailOpenMySqlTest` + `mall-user-center ProductSnapshotClientTest`，再跑一次经网关的四边贯通冒烟。
9. **共享注解被批量 import**：多个服务的 domain/dto 里出现 `import com.mall.common.support.MemberId;` 但文件内无任何使用（例：`mall-user-center/src/main/java/com/mall/usercenter/domain/Address.java:9`）。不影响运行，但让"谁真的在用 `@MemberId`"变难 grep。

### 9.3 与网关的关系

- 网关**不依赖** `mall-common`（`mall-gateway/pom.xml` 无该依赖），因此 `X-Trace-Id` 的**头名与形状闸门有两份实现**：网关 `support/TraceIdFilter`（WebFlux `GlobalFilter`，显式打日志、不打 MDC）与本模块 `web/TraceIdFilter`（servlet，打 MDC）。两处任一改动都要同步（记录也写着"网关那份是 WebFlux `GlobalFilter`，**不动**"，`微服务代码规范.md:195`）。
- 网关的名称服务、限流、鉴权全部与共享内核无关；改 `mall-common` 不影响网关行为。
