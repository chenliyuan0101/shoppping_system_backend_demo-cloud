# `mall-admin` 代码解析

> **定位**：管理端 BFF（P7）。它只自持**一张表 + 两个跨服务 Redis 键**：管理员登录态（`/api/admin/auth/**`），
> 以及网关 403 判据的**唯一写入方**（`mall:cache:admin:status:{id}`、`mall:token:ver:admin:{id}`）。
> **边界**：本服务**不拥有会员/订单/商品数据**——看板与会员管理的每个数字都靠出站调 trade / product / user-center 的内部契约（`/internal/v1/**`）现取现拼；
> `/api/admin/{product,category,brand}` 归 product、`coupon` 归 marketing、`stat|mq` 归 trade、`es` 归 search，**都不经过本服务**（`AdminApplication.java:15-16`）。
> **范围**：`src/main/java` **57 个文件 / 3868 行**；测试 **12 个可运行测试类 / 115 例**（+1 抽象用例基类、6 个支撑类）。统计命令：`Get-ChildItem src\main\java -Recurse -File -Filter *.java | ForEach-Object { (Get-Content $_).Count } | Measure-Object -Sum`。
> 例数口径：直接 `@Test` 105 例 + `AbstractDashboardDeadDependencyTest` 被 3 个子类继承的 15 例，与 `target/surefire-reports` 的 12 行 `Tests run`（合计 115）逐类吻合。
> **与其它文档的分工**：本文只讲"代码怎么组织、每个类怎么实现、改哪里会坏"；端口/路由/数据属主见 `系统说明.md`，请求生命周期见 `系统流程与三大核心功能实现.md`。本文结论都对着源码核过（含行号），未读到实据的一律不写。

自持 / 薄转发的分工：`/api/admin/auth/**` **本域自持**（查 `mall_admin.sys_user`、签令牌、bump 版本、写状态缓存）；`/api/admin/dashboard/**` 是**薄转发 + BFF 组装**（三域统计并行取数 → 拼看板视图）；`/api/admin/member/**` 是**薄转发**（分页主查与订单补数在下游，BFF 只做"两次调用 + 拼 VO + 失效看板缓存"）。
## 2. 分层与包职责

- **`controller`**：只做参数绑定 + 委托 + 包 `ApiResponse`，**不放业务判断**——连 `days/limit` 的钳制都不在这里（属主域做，`AdminDashboardController.java:28-30`）。唯一带语义的一行是 `AdminMemberController.java:63-64`：日期换算成半开区间（起=当天 00:00，止=**次日** 00:00）。
- **`service` / `service.impl`**：接口承载契约与文档（注释最厚的地方），实现承载并发/缓存/降级/事务边界。
- **`client`**：只有 `*Api` + `*Client` 一种形状。`*Api` 用 `@HttpExchange` 声明路径与泛型，**不处理错误语义、不打日志、不降级**；`*Client` 干三件事：连接装配（`@LoadBalanced` builder + 超时）、错误语义、形状适配。
- **`config`**：组装根。`MybatisPlusConfig` 手动装配 + `@MapperScan("com.mall.admin.mapper")`（**只扫本包**，不去扫别人的库边界）；`AdminIdentityResolver` 是解析器而非过滤器。
- **`support`**：无业务语义的工具与"自持契约面"；**架构规则禁止它依赖 `controller`/`internal`/`client`/`service`**（`CodeStyleTest#supportDoesNotDependOnOuterLayers`），`domain` 同理。
- **组装根为什么在 `config`**：本服务是独立 Maven 工程（无聚合 pom），启动类只负责注解 + 扫描 `com.mall.admin.**`（`AdminApplication.java:39-41`），所有 `@Bean`/拦截器装配落在 `config`。
## 3. 核心类详解

### 3.1 入口层：`AdminAuthController`（58 行）+ `AdminMemberController`（79 行）

- `AdminAuthController`：三个映射与单体逐字相同。**唯一的实现差异**是单体把裸 token 当参数传给 Service，本服务改成"Service 自己从身份解析器取当前管理员"——P7 §2 之后身份可能来自网关注入的头，服务端手里没有也不该有原始令牌（类注释）。`login` 标 `@RateLimit(scope="admin_login", limit=10, windowSeconds=60)`（`:42`，撞库防护不许因搬家变松）。
- `AdminMemberController` 两处最容易"顺手改掉"的细节：`createDateEnd.plusDays(1).atStartOfDay()`（`:63-64`，止那天是**含**的，少一个 `plusDays` 就过滤掉"今天"）；状态在**请求体**里（`@RequestBody StatusRequest`）而非 query 参数——C1 基线里这两条用例是带体的。
- 覆盖：`AdminAuthControllerTest`（15 例切片）、`AdminAuthApiMySqlTest`（26 例真库）、`AdminMemberApiStubTest`（11 例）。

### 3.2 登录态唯一判定链：`config/AdminIdentityResolver` + `support/AdminSession`

**判定阶梯（顺序即安全语义，`AdminIdentityResolver.java:79-103`）**：

```
① 有 X-Gateway-Auth？
   有 → 必须等于 mall.gateway.auth-token（MessageDigest.isEqual 常量时间比较，:115-118）；
        不等 / 未配置 → 401「未登录」，**不回落**本地验签（带了伪造凭据就是攻击形状）
      → 取 X-Admin-Id（不是数字 → 401「未登录」）+ X-Admin-Ver（缺失按 0）
      → AdminSession.requireAdminById(adminId, ver) 完成 ③④⑤
   没有 → require-gateway-identity=true → 401「未登录」（目标形态，fail-closed）
          require-gateway-identity=false（默认）→ AuthHeader.bearer → AdminSession.requireLocalToken（过渡态）
```

| `mall.admin.auth.require-gateway-identity` | 含义 | 直连 8108（无身份头） | 经网关 |
|---|---|---|---|
| `false`（默认、当前交付） | **优先网关身份，缺失时回落本地验签**：与单体逐字相同的 `Authorization` 老路仍可用 | `Authorization` 有效即通过 | 走身份头，不重复验签 |
| `true`（目标形态，待网关路由切过来才可开） | **只认网关注入的身份** | 一律 401「未登录」 | 正常 |

⚠️ 共享凭据未配置时**不阻止启动**，只 `log.warn`（`:64-69`）：此时任何 `X-Gateway-Auth` 都不认、退化为本地验签；若同时开了 `require-gateway-identity=true` 则全部 401（fail-closed，不会静默越权）。切 `true` 的前提是网关路由已指向本服务，否则管理端登录会被自己关在门外（`application.yaml:78`）。
**`AdminSession`（122 行）：两条入口共用同一段 ③④⑤（`:74-91`）**

| 顺序 | 判据 | 失败文案 |
|---|---|---|
| ① | JWT 验签 + 有效期（仅 `requireLocalToken`，走 `JwtUtil.parse`） | 401 `登录已失效，请重新登录` |
| ② | `typ` 必须是 `admin`（仅 `requireLocalToken`） | 401 `登录已失效，请使用管理员账号登录` |
| ③ | `sys_user` 查得到 | 401 `登录已失效，请重新登录` |
| ④ | `status == EnableStatus.ENABLED` | **403** `账号已被禁用` |
| ⑤ | 令牌版本号一致（`TokenVersionService.matches`） | 401 `登录已失效，请重新登录` |

**④ 必须排在 ⑤ 之前**：反过来会把"已禁用 + 版本已 bump"的管理员从 403 变成 401（文案漂移）；网关 `AdminIdentityFilter` 用同一顺序（`AdminSession.java:23-24` 有原话）。**请求级缓存**以"解析入口 + 凭据"为键存进 `RequestAttributes`（`ATTR_ADMIN`，`:43`；`record Resolved(key, admin)`，`:120`）——一次请求里拦截器解析一次、`/me` 再取一次不重复查库/读 Redis，且同一请求内换凭据不会被误复用。**两条入口共用 ③④⑤ ⇒ 不可能出现"网关路径比本地路径宽松"**（类注释 §"P7 §2 的两条入口"）。

### 3.3 `service/impl/AdminAuthServiceImpl`（113 行）——login / me / logout

`login(AdminLoginRequest)`（`:59-76`）四步，**顺序不许变**：① 账号或密码为空 → `400 请输入账号和密码`（`StringUtils.hasText` 判空，用户名 `trim()` 后查）；② 查不到 **或** BCrypt 不匹配 → `401 用户名或密码错误`（**不区分**两种失败，避免账号枚举）；③ `status != 1` → `403 账号已被禁用`（**在口令校验之后**）；④ `adminStatusCache.putEnabled(id, username)`（`:72`）+ 签发 `createToken(id, username, TYPE_ADMIN, tokenVersionService.current(TYPE_ADMIN, id))`。
**唯一增量就是第 ④ 步**：它是"网关手里唯一那份管理员状态"的正常路径来源；没有它，网关读到"键不存在"（fail-open），403 只能靠对账任务在 10s 内补。⚠️ 写缓存失败**不影响登录**（`CacheService` 全链路 fail-open，`AdminAuthCacheDisabledMySqlTest` 专门钉住）。
`getAdminInfo()`（`@Transactional(readOnly = true)`）只做 `toInfo(currentAdmin())`；`currentAdmin()`（`:94-103`）从 `RequestContextHolder` 取请求交给 `AdminIdentityResolver.resolve`，无 HTTP 上下文时抛 401「未登录」。
`logout()`（`:85-91`）**只 bump、不动状态缓存**（`tokenVersionService.bump(TokenVersionService.TYPE_ADMIN, admin.getId())`）——登录态作废靠版本号，账号状态靠状态缓存，两件事互不替代（`AdminAuthService.java:33`）。

### 3.4 `service/impl/AdminStatusServiceImpl`（130 行）——**禁用判据的写入方**

**`updateStatus(long, Integer)`（`:94-129`，`@Transactional`）**

| 步 | 行为 | 文案 |
|---|---|---|
| 1 | `selectById` 查不到 → **先 `evict` 状态缓存**再抛 | 404 `管理员不存在` |
| 2 | 状态值不是 0/1 → 400 | `状态值仅支持 0禁用 1正常` |
| 3 | `updateById` 落库（只更新 status 一列）；然后提交后写缓存 | — |
| 4 | `TxCallbacks.afterCommitOrNow`：**禁用写 0 / 启用写 1**（写，不是删） | — |
| 5 | 且本次是**启用→禁用跃迁**（`enabledToDisabled`，`:110-111`）时再 `bump` + `log.warn` | — |

```java
TxCallbacks.afterCommitOrNow(() -> {
    if (status == EnableStatus.DISABLED) adminStatusCache.putDisabled(adminId, username);  // 写而不是删：网关要靠这个值产出 403
    else                                  adminStatusCache.putEnabled(adminId, username);
    if (enabledToDisabled) tokenVersionService.bump(TokenVersionService.TYPE_ADMIN, adminId);   // 双保险
});
```
**为什么放在 `afterCommit`**：事务回滚了就不该让外部世界看见"禁用"（否则网关会给其实没被禁用的管理员回 403，直到 TTL 到期）。**跃迁判据用"库里的旧值"**，所以"禁用→禁用"重复调用**不会再 bump**（否则每次改状态都把管理员踢下线）。⚠️ **本方法目前没有 HTTP 入口**（全仓只有测试调它；`AdminStatusService.java:31` 注明"未来『禁用管理员』端点的落点，本批没有 HTTP 入口"）——这正是 `reconcile()` 必须是硬前置的原因。
**`reconcile()`（`:64-91`）——10s 对账的判定规则**

| 库 vs 缓存 | 动作 |
|---|---|
| 缓存存在且 `status` 与库一致 | **什么都不做**（收敛，不触碰 Redis，不计入返回值） |
| 库 = 1（启用） | `putEnabled`（**不** bump） |
| 库 = 0（禁用）**或缓存键不存在** | `putDisabled` **并且** `bump` + `log.warn` |

**为什么"每次补写都 bump"也是对的**（类注释）：状态缓存 TTL 10 分钟，到期后键消失 ⇒ 网关在那段时间是 fail-open；下一轮对账重新写禁用值并**再 bump 一次**——这不是重复劳动，而是"缓存缺失窗口"的主动补偿（代价：每 10 分钟一次 INCR，而被禁用的管理员本来就登不上）。收敛性由"缓存值 = 库值"保证（用例 `reconcile_isConvergent_secondRunDoesNotBumpAgain`）。对账**不在事务里**（只读一行 + 写 Redis），所以立即执行。覆盖：`AdminStatusCacheMySqlTest`（15 例，其中 4 例专打 `reconcile`）。

### 3.5 `support/AdminStatusCache` + `support/TokenVersionService` + `support/JwtUtil`——键的写入方与令牌

**`AdminStatusCache`（89 行）**：`mall:cache:admin:status:{adminId}` → `AdminStatusVO` JSON，**TTL 10 分钟**（`:45`）。

| 方法 | 行为 |
|---|---|
| `get(long)` | `cacheService.getJson(...)`；未命中/Redis 不可用 → `null` |
| `put(id, username, status)` | `status == null` 时**什么都不写** + `log.warn`（写一份取不到 status 的 JSON 会让 403 静默失效，`:60-66`） |
| `putEnabled` / `putDisabled` | 写 1 / 写 0 |
| `evict(long)` | 删——**只用于"管理员记录本身消失"**；⚠️ 禁用**不要**用它（`:81-85`） |

⚠️ **与会员侧 `MemberStatusCache` 的关键差别**：会员侧禁用"只删不写"（会员 401 文案由下游查库产出）；管理端相反——**403 由网关产出，而网关只有这一份信息**，所以禁用必须**写 0**：删掉键 = 网关 fail-open = 403 永远不出现。
**`TokenVersionService`（60 行）**：key `mall:token:ver:admin:{id}`，**TTL 30 天**（`:27`）。`current` 在 Redis 不可用/值非数字时返回 0（与"未启用 Redis"行为一致）；`bump` 是 `increment`、返回 <0 时归 0 且不抛异常；`matches` 在 `!cacheService.available()` 时**直接返回 true**（降级：不因 Redis 故障把管理员全部踢下线）。它是"禁用立即生效"的**第二道保险**（第一道是状态缓存的 403 判据）：缓存被清/写错/TTL 到期都不影响旧令牌作废。
**`JwtUtil`（170 行）——令牌签发方**：本类必须与网关/单体**逐字一致**（P7 §3 硬要求）：header 恒 `{"alg":"HS256","typ":"JWT"}`、base64url **无填充**；payload 顺序 `sub,name,typ,ver,iat,exp`（顺序不影响判定，但逐字可让"同一秒/同一版本/同一管理员"签出的令牌**字节相同**，便于对撞验证）；`exp = iat + expireHours*3600`（`mall.jwt.expire-hours:24`），**没有**时钟宽容窗口；验签用 `MessageDigest.isEqual`；失败一律 `401 登录已失效，请重新登录`。**构造时 fail-fast**（`:49-60`）：`mall.jwt.secret` 缺失或短于 32 位 ⇒ `IllegalStateException` 拒绝启动（否则最容易发生的事故是"用空密钥验签，把所有请求判成未登录"）。`createToken` 的 `ver` **必须传当前版本号、不要写死 0**（`:62-66`）：版本已 >0 时写死 0 的令牌会被自己立刻判为失效。

### 3.6 `task/AdminStatusReconcileTask`（82 行）

```java

           initialDelayString = "${mall.admin.status-reconcile-initial-delay-ms:10000}")
public void reconcile() {
    if (!enabled) return;                       // mall.admin.status-reconcile-enabled:true（生产默认 true）
    try { int fixed = adminStatusService.reconcile(); ... }              // 整个方法体被 try/catch 包住
    catch (Exception e) { log.warn("...（fail-open，下一轮重试）: {}", e.getMessage(), e); }
}
```
**为什么必须有它**：今天**没有任何"禁用管理员"的入口**（禁用 = 值班人员直接 `UPDATE sys_user SET status = 0`），只靠"改状态时写缓存"，缓存会永远停在登录时写的 `status=1`。**为什么是轮询而不是库变更通知**：变更根本不经过本服务，没有任何事件可订阅。catch 保证绝不让定时线程抛异常（抛出去只会让下一轮更晚跑）。⚠️ 少了启动类上的 `@EnableScheduling`（`AdminApplication.java:40`）本方法**永远不会执行，而且不报错**——那正是"缓存永远是旧的"这类静默失效的形状。测试期用 `mall.admin.status-reconcile-enabled=false` 关掉调度、改为**直接调用服务**（`src/test/resources/application.properties:25`）。覆盖：`AdminStatusReconcileTaskTest`（4 例）+ `AdminStatusReconcileSchedulingTest`（2 例，真上下文里把间隔压到 200ms 断言"确实被调度执行"）。

### 3.7 `service/impl/AdminDashboardServiceImpl`（322 行）——看板并行聚合

**① 并行：必须"先全部 submit、再逐个 join"**（`:118-125`）

```java
CompletableFuture<OrderSummaryVO> tradeFuture   = submit(DOMAIN_TRADE,   degraded, tradeStatClient::summary);
CompletableFuture<Long>           productFuture = submit(DOMAIN_PRODUCT, degraded, productStatClient::enabledCount);
CompletableFuture<Long>           userFuture    = submit(DOMAIN_USER,    degraded, userCenterMemberClient::count);
OrderSummaryVO order = tradeFuture.join();          // 三个 submit 都发出去之后才 join
```
写成 `join(submit(...))` 三行就是**串行**（第二个任务在第一个完成后才提交）。判据可执行：用例用三个会 sleep 的环回桩量**请求到达的重叠度**（峰值并发 == 3）与**墙钟时间**（≈最慢的一个，而非三者之和）。
**② 降级：每请求恰好一条 WARN**

| 端点 | 不可用时的兜底 | 理由 |
|---|---|---|
| `summary` | 挂掉那一域的字段回 **0**（不是 null：单体是原始 `long`）；**各域独立降级** | 挂了交易域不影响"在架商品数"仍是真的 |
| `trend` / `top?type=sales` | 唯一来源是交易域 / 商品域 ⇒ **空数组** | — |
| `top?type=amount` | 交易域给金额、商品域补标题 ⇒ **任一不可用都空数组** | 宁可不给榜单，也不要把"商品服务挂了"显示成"商品已删除"（那是一个**看起来正常**的错误结论） |

`Degradation`（`:297-321`）是请求内降级账本（`ConcurrentHashMap`，三个取数并发跑），原因取 `getMessage()` 而非完整栈；收尾**只留一条 WARN**：
```java
log.warn("看板降级: endpoint={} 不可用的依赖={} ⇒ 缺的那部分按 0/空数组返回"
         + "（HTTP 200 / code=0 / 键路径集合不变；本次结果不入缓存）",
        endpoint, new TreeMap<>(failures));   // TreeMap：输出顺序稳定（trade < product < user）
```
判据可执行：`logs.warnMessages()).hasSize(1)`，且那条日志必须点名挂掉的域——"每请求一条"可断言，"每个依赖一条"会让日志条数随故障数变化。
**③ `submit` 捕获 `RuntimeException`**（`:252-267`）：三个 `*Client` 已把传输异常与非 0 业务码统一成 `BusinessException`，所以"连不上"与"下游报错"降级策略相同；**线程池已关闭/队列拒绝**也走同一条降级路径——容器停机时仍然不许 500。
**④ 缓存：短 TTL + 主动失效，且降级结果绝不入缓存**（`:269-276`）：`cacheIfHealthy` 先看 `degraded.any()`，为真就只 `logWarn` 并 `return`，否则才 `dashboardCache.put`。把"trade 挂了 ⇒ 四个字段全 0"缓存 60 秒，等于让一次瞬时故障变成一个分钟的对外错误结论，而且形状完全正常、**没有任何迹象**。
**⑤ 不给 future 加 `orTimeout`**：每个客户端都设了连接 300ms / 读 2500ms，那就是"各自设短超时"的落点；再加一层只会引入第二个上限，两者不一致时更难解释。
**⑥ 一个容易误读的细节**（`:231-234`）：`top?type=amount` 里 `spu == null ⇒ title = "商品已删除"` 是**单体口径的业务值，不是降级占位**（"调用成功但查不到该 SPU"），`mainImage` 为 null 同理；降级（商品域整体不可用）走"空数组"分支。`type` 判据与单体逐字一致：`"amount".equalsIgnoreCase(type)`，**非 amount 一律按 sales**（`:178-179`）。列表型缓存读取用显式 `TypeReference`（`:278-288`）——泛型擦除下 Jackson 只会反序列化成 `List<LinkedHashMap>`，随后 `ClassCastException` 且编译期看不出来。
覆盖：`AdminDashboardStubTest`（14 例）、`AdminDashboard{Trade,Product,User}DownTest`（各 5 例，继承 `AbstractDashboardDeadDependencyTest`）。

### 3.8 `support/DashboardCache`（115 行）——看板缓存与"代号"

键形状 `v{代}:{后缀}`：`v3:summary` / `v3:trend:7` / `v3:top:sales:10`。

| 方法 | 行为 |
|---|---|
| `generation()` | 读 `mall:cache:admin:dashboard:gen`；键不存在/不可解析/Redis 挂 ⇒ **0**（键不存在与代 0 是同一件事） |
| `key(suffix)` | 当前代的条目键（**算键的地方只有这一处**） |
| `evictAll()` | `INCR` 代号（TTL 30 天）；Redis 不可用时返回 -1 |
| `get/put` | `cache-enabled=false` ⇒ 读一律 `null`、写直接 return；TTL 默认 60s |

**为什么主动失效用 INCR 而不是删键**：要删的是"所有参数组合"（`trend:1..30` × `top:2×1..20`），既枚举不完也不该在生产跑 `KEYS`；带"代"的键换代后**立刻不可达**，旧代由 TTL 自然回收。这与"令牌版本号 bump ⇒ 旧令牌立刻失效"是同一手法——**同一个仓库里不要有两种失效风格**。**TTL 实测区间**：`CacheService.set` 对 TTL 加 ±15% 抖动（防雪崩），60s 实际落在 **51~69 秒**，用例断言的是这个区间而非字面 60。

### 3.9 `config/DashboardExecutorConfig` + `config/MdcPropagatingExecutor`——线程池与 traceId

```java
@Bean(name = DASHBOARD_EXECUTOR, destroyMethod = "shutdown")
public ExecutorService dashboardExecutor(@Value("${mall.admin.dashboard.parallelism:8}") int parallelism) {
    int size = Math.max(3, parallelism);   // 至少 3：一次 summary 就要同时占 3 个线程，否则"并行"是假的
    ThreadFactory factory = runnable -> { Thread t = new Thread(runnable, "dashboard-agg-" + seq.incrementAndGet());
                                          t.setDaemon(true); return t; };   // 看板线程不该阻止 JVM 退出
    return new MdcPropagatingExecutor(Executors.newFixedThreadPool(size, factory));
}
```
**不用 `ForkJoinPool` 公共池**：公共池是所有代码共用的（连 `parallelStream` 也在里面），看板一次占 3 个线程会挤掉"跟我无关的别人的并行度"；单独池的**线程名**让"看板在并发拉数"在日志里一眼可见。**`newFixedThreadPool` 是无界队列**：池满时**排队**而不是拒绝——对"慢一点也要有答案"的读路径正合适，真正的上界由调用超时给出。
`MdcPropagatingExecutor`（95 行）**只重写 `execute`**（`AbstractExecutorService.submit` 内部走 `newTaskFor` → `execute`，所以 `submit`/`invokeAll` 自动被覆盖）：提交时 `MDC.getCopyOfContextMap()` 抓快照，工作线程执行前 `setContextMap` 装回去、`finally` 里**恢复而不是清空**（线程池线程复用，不还原会把上一个任务的 id 泄漏给无关任务）。没有它：工作线程里 `traceId` 为空 ⇒ 三条出站**不带 `X-Trace-Id`** ⇒ "网关 → mall-admin → trade"三段日志串不起来（类注释记了实测现象）。

### 3.10 `service/impl/AdminMemberServiceImpl`（175 行）——会员管理

### 3.12 `config/WebConfig` + `config/AdminAuthInterceptor` + `config/RateLimitAspect`

`registry.addInterceptor(adminAuthInterceptor).addPathPatterns("/api/admin/**").excludePathPatterns(LOGIN_PATH)`，其中 `LOGIN_PATH = "/api/admin/auth/login"`（`WebConfig.java:30`）。`AdminAuthInterceptor#preHandle` 只做一件事：`adminIdentityResolver.resolve(request)` 再把 id 写进请求属性 `AuthAttribute.ADMIN_USER_ID`；⚠️ **它不自行验签**——拦截器里再写一遍校验就会长出第二套口径（P7 §2 反复强调"管理端登录态只在一处判定"）。⚠️ **尾斜杠** `/api/admin/auth/login/` **不在**放行名单里（Spring 6+ 不做尾斜杠匹配）——该形状经单体是 404、经网关过滤器是 401「未登录」，本服务刻意不改这个口径（`WebConfig.java:18-19`）。

## 5. 出站与入站边界

**出站**（三对，明细见 §3.11）：目标 `lb://mall-trade` / `lb://mall-product` / `lb://mall-user-center`，超时统一 300ms/2500ms；失败语义"传输失败与空响应 → 500 统一文案、非 0 业务码原样透传"；**降级策略在调用方**（看板：各域独立降级 + 一条 WARN；会员列表：补数降级为 null + 一条 WARN）。不以 `lb://` 开头时**绕过服务发现直连**（`http://127.0.0.1:9` 就是"依赖不可用"的演练方式）。

**MQ**：**无**，不发布也不消费任何消息（`pom.xml` 无 kafka/rabbit 依赖，无 `mq` 包，无 `@KafkaListener`/`@RabbitListener`）。
## 6. 定时任务与异步

| 类 | 触发（真实表达式 + 默认值） | 做什么 | 幂等性 |
|---|---|---|---|
| `AdminStatusReconcileTask#reconcile` | `@Scheduled(fixedDelayString = "${mall.admin.status-reconcile-interval-ms:10000}", initialDelayString = "${mall.admin.status-reconcile-initial-delay-ms:10000}")`；开关 `mall.admin.status-reconcile-enabled:true` | 读全部 `sys_user.status`，把状态缓存纠正到与库一致；"库=0 或缓存键缺失"时**再 bump 一次令牌版本** | **收敛**：缓存值=库值时什么都不做、不触碰 Redis、不 bump（返回值是本轮修正条数）；`fixedDelay` 保证"上一轮结束到下一轮开始"，不堆积 |

**异步只有一个落点**：`DashboardExecutorConfig` 的 `dashboardExecutor`（bean 名 `DASHBOARD_EXECUTOR`，构造器 `@Qualifier` 注入），池大小 `Math.max(3, parallelism)`（默认 8）、`destroyMethod="shutdown"`，外面包一层 `MdcPropagatingExecutor`。本服务**没有 `@Async`**、没有自建 `TaskScheduler`。

## 9. 坑与已知边界（全部能在代码里指到）

1. **今天没有任何"禁用管理员"的 HTTP 入口**（`AdminStatusService.java:31`）。禁用 = 值班人员直接 `UPDATE sys_user SET status = 0`，所以**对账任务是硬前置**：没有它，路由切到本服务后单体的 `AdminAuthInterceptor` 退出链路，被禁用的管理员**还能用**。
2. **状态缓存 TTL 老化 ⇒ 网关存在 fail-open 窗口**：条目 10 分钟到期后键消失、网关放行；补偿是"下一轮对账（默认 10s）重新写禁用值**并再 bump 一次**"（`AdminStatusCache.java:30-34` 如实写明代价与补偿）。
3. **两个开关的边界**：`mall.gateway.auth-token` 未配置不阻止启动，只 `log.warn`（`AdminIdentityResolver.java:64-69`）——此时网关注入身份一律不认 → 退化本地验签；若同时开了 `require-gateway-identity=true`，则**所有后台接口 401**（fail-closed，不会静默越权）。因此切 `true` 的前提是网关路由已指向本服务（`/api/admin/auth/**`），否则管理端登录被自己关在门外（`application.yaml:78`）——这是本服务唯一"两处配置必须同批改"的开关。
4. **`mall.internal.token` 不一致的症状是"看板永远是 0，但没有任何报错"**：下游 `InternalApiAuthInterceptor` 是 fail-closed 回 403，而被 BFF 当成"该域不可用"降级成 0（`application-dev.yaml:51-53` 称之为"配置里的坑"）。
5. **看板缓存键与别的测试上下文共享真 Redis**：`BffStubTestBase` 每个用例前 `dashboardCache.evictAll()` 换代——不换代的话另一上下文写的 `v{N}:summary` 会被本类读到，那是**假绿/假红**的经典来源（`BffStubTestBase.java:20-25`）。
6. **`commentCount` 恒为 null**：评价表已归 `mall-review`，单体里这个数也没有来源；字段保留只为不改响应形状，回填要等 BFF 调 review 的内部端点（盘点报告 R9）——**本批不回填**（`MemberAdminVO.java:41-50`）。
7. **列表页订单口径是"值层面的增强"**：单体"列表不补数、只有详情补"（列表两项恒 null），本批列表也补数；`MemberAdminVO` 的**键集合一字不差**，前端列表页也不渲染这两个字段（只有详情弹窗渲染），所以 C1 指纹（键路径/code/文案/id 集合）不变（`AdminMemberServiceImpl.java:42-45`）。
8. **`GET /api/admin/member/page` 的默认值参与下游请求体**：`PageQuery` 默认 1/10，默认值不同 ⇒ 不传分页参数会取到不同的页（`PageQuery.java:9-11`）；本服务**只承载默认值与文档、不做钳制**（钳制在属主域 `PageKit`）。
9. **`/api/admin/auth/login/`（尾斜杠）不在放行名单**：Spring 6+ 不做尾斜杠匹配，该形状经单体是 404、经网关过滤器是 401「未登录」；本服务刻意不改（`WebConfig.java:18-19`）。
10. **两处注释里的过期引用/说明**（读到的实据，不是推测）：`AdminDashboardServiceImpl.java:311` 与 `DashboardVO.java:20` 都引用用例类名 `AdminDashboardConcurrencyStubTest`，**该类在仓库里不存在**（现名 `AdminDashboardStubTest`）；`OpenApiConfig.java:35` 的 description 写着"看板与会员管理由 P7 后续批次交付"、`AdminApplication.java:12-13` 也把看板/会员写成"后续（P7 后半）"——都是**完工前的说明**，功能已实现在本模块。
11. **定义但无人调用/未使用的东西**：`AdminIdentityResolver#gatewayTokenConfigured()`（自述"运维/自检用"，`:110-113`）；`MdcPropagatingExecutor#drainForTest()` 恒返回空列表（`:91-94`，自述"仅供测试/排障"）；`RateLimitAspect` 的 `By.USER` 分支（后台登录用默认 `By.IP`，该分支会解析网关注入身份、解析不到回落 IP，`:82-89`，属预留能力）。
12. **改动后的最小验证集**：`mall-admin` 的 115 例 + 与网关的两条契约（key 名/极性、4 条文案逐字）+ 一次经网关的冒烟（管理员登录 → 看板三端点 → 会员列表/启停）+ traceId 三段贯通（网关 → mall-admin → trade）。
