# mall-review 代码解析

> 一句话定位：`mall-review` 是**评价域的属主**——它持有商品评价表 `pms_comment` 与"待评价"读模型 `review_pending_item`，负责发表评价、商品评价展示、我的评价，并把 trade 的 `order.finished` 事件投影成待评价行；订单/会员的数据它只要**事件带来的快照**，不回头查、也不回写。
> 范围：`backend/mall-cloud/mall-review/src/main/java` 下 **44 个文件 / 2786 行**（不含 `resources`）；测试 **7 个类 / 41 例**（`@Test` 计数）。
> 与其它文档的分工：本文讲"代码怎么组织、每个包在干什么、核心类怎么实现、改代码要注意什么"；端口/路由/数据属主的系统级视图见 `系统说明.md`，一次请求的生命周期见 `系统流程与三大核心功能实现.md`。本文每条结论都对着源码核过（写成 `类#方法` 或 `路径:行号`）；无法证实的显式标注「（推测：…）」。

## 3. 核心类详解

### 3.1 `service/impl/CommentServiceImpl`（280 行）★ 提交评价的全部规则

一句话：提交评价的全本地实现（读模型校验 + 昵称快照 + 评价写入 + CAS 闸门），以及两条只读路径。

**`submit(Long memberId, SubmitCommentRequest request)`（`:93-161`，`@Transactional`）** 的顺序即语义：

| # | 判据 | 落点 | code / 文案 |
|---|---|---|---|
| ① | `items` 为空/缺失 | `requestValidator.check(request)`（`:97`）← `SubmitCommentRequest.items` 上的 `@NotEmpty` | 400 `请填写评价内容` |
| ② | orderNo 空文本 / 读模型无行 / 行不属于该会员 | `loadOrderItems`（`:175-189`） | 404 `订单不存在` |
| ③ | 最早收货时间为 null 或晚于 `now` | `:103-106` + `orderFinishTime`（`:198-204`） | 409 `订单完成后才能评价` |
| ④ | 收货时间早于 `now - limitDays` | `:108-110`，天数来自 `@Value("${mall.comment.limit-days:90}")`（`:86`） | 409 `已超过 90 天可评价期限` |
| ⑤ | 明细不属于该订单 | `:123-125` | 400 `评价条目不属于该订单` |
| ⑥ | 同一请求内重复提交同一条明细 | `seen` 集合（`:120,126-128`） | 400 `同一订单明细不能重复评价` |
| ⑦ | **分支 A**：读模型快照 `commented == 1` | `:130-134` | 409 `该商品已评价` |
| ⑧ | `rating` 非 1~5 | `:135-137` | 400 `评分须为 1~5` |
| ⑨ | **分支 B**：CAS 抢占影响 0 行 | `:155-159` | 409 `该商品已评价` |

```java
commentMapper.insert(comment);                                                             // :151 先落评价行（拿到自增 id）
int claimed = reviewPendingItemMapper.claim(orderItem.getOrderItemId(), comment.getId());   // :155 CAS 抢闸门
if (claimed == 0) { throw new BusinessException(409, "该商品已评价"); }                      // :156-159 → 整批回滚
```

- **为什么先 INSERT 后 CAS**（类注释 `:65-69`）：闸门 UPDATE 要写 `comment_id`（"这条明细最终评的是哪条评论"，对账需要），而评价 id 要等 INSERT 才由数据库给出；抢不到就抛 409 ⇒ **整个事务回滚**把刚插入的评价行一起撤销，对外表现与"先抢后写"完全一致（`CommentApiMySqlTest:353-354` 断言"抢失败不能留下半条评价"）。**事务边界**：一条 UPDATE + 一条 INSERT（多明细重复 N 次）同事务，任一明细失败 ⇒ 整批回滚（`CommentApiMySqlTest:293-296`）。
- **昵称快照只取一次**（`:115-116`）：`memberSnapshotClient.nickname(memberId)` 在循环外调用；注意它在 ⑤⑥⑦⑧ 这些**逐条**校验之前——一个明细号写错的请求也已经发出了那次出站调用（受 1.5s 读超时约束）。
- **两个 409 分支刻意不合并**（`:131-133`、`:157`）：分支 A 是"读模型预检"、分支 B 是"并发抢占失败"，文案相同、触发条件不同。**`seen` 的存在理由**（`:118-120`）：`itemMap` 里的对象不会因为"上一轮把它置 1"而变化，只靠 `commented` 判断会放行两次。
- **字段与归属口径**：`images` 用 `JsonKit.toJson(list)` 存 JSON 字符串（`:148-149`）、`status` 恒为 `CommentStatus.VISIBLE`（`:150`，一期直接展示）；`loadOrderItems` 先按 `orderNo` 等值查、再在内存里按 `memberId` 过滤（`:180-184`），别人的行不进 `itemMap` ⇒ 落到循环里就是 400（`:172-173`）；找不到任何"我的"行 ⇒ 404，**不区分"订单不存在"与"不是你的"**（`:167-171`，`CommentApiMySqlTest#submit_orderOfAnotherMember` 守这条）。

**`productComments(Long spuId, long pageNum, long pageSize)`（`:210-240`，只读事务）**：页码/页大小收敛（`PageKit.page`、`size = min(50, max(1, pageSize))`，`MAX_PAGE_SIZE = 50` 见 `:77,213-214`）；三条 SQL（好评数 `rating >= 4`、总数、分页列表）**都带 `status = VISIBLE`**（`:216-223`），排序 `create_time desc, id desc`、分页 `.last("LIMIT x,y")`；好评率 `total == 0 ? 100 : round(goodCount*100.0/total)`（`:238`）——**没有评价时是 100**（`CommentsResult:13-15`）；昵称读本表快照、空则 `"匿名用户"`（`:231-233`）。

**`mine(Long memberId, long pageNum, long pageSize)`（`:246-279`，只读事务）**：`spuTitle` **不回头查商品域**，而是拿 `Comment.orderItemId` 去 `reviewPendingItemMapper.selectBatchIds(...)`（主键就是 order_item_id）读 `spu_title` 下单快照（`:257-265`）；读模型里没有这条明细 ⇒ `null`。覆盖测试：`CommentApiMySqlTest`（17 例）。

### 3.2 `mapper/ReviewPendingItemMapper`（78 行）★ 两条自定义 SQL 就是全部防线

| 方法 | SQL 行为 | 契约 |
|---|---|---|
| `upsert(ReviewPendingItem)`（`:43-52`） | `INSERT ... ON DUPLICATE KEY UPDATE order_item_id = order_item_id` | 返回 **1 = 新增 / 0 = 已存在**；自赋值是"什么都不改"（`:20-28`：不用 8.0.20 起废弃且会触发 `ON UPDATE CURRENT_TIMESTAMP` 的 `VALUES(col)`；更不用会把数据超长等真错误一起吞掉的 `INSERT IGNORE`） |
| `claim(long orderItemId, Long commentId)`（`:72-77`） | `UPDATE review_pending_item SET commented=1, comment_id=#{commentId} WHERE order_item_id=#{orderItemId} AND commented=0` | **影响行数 = 并发凭证**：1 = 抢到、0 = 已被评价（含回填的 `commented=1` 行）⇒ 调用方抛 409 |

这条 CAS 成立的物理前提是主键：`order_item_id` 是 PK（`V1__baseline.sql:51`），`InternalReviewApiMySqlTest:64-71` 专门断言，理由写在断言消息里——"没有唯一索引这条判定不成立"。

### 3.3 `mq/OrderFinishedConsumer`（103 行）★ 待评价读模型的唯一写入方

`onOrderFinished(Message message, Channel channel)`（`:64-102`）的四条手动 ack 出口：

```
① payload 解析失败                 → publishRawToDlq（保留原始字节）→ ack                     :70-77
② event == null / memberId == null → 只打 WARN → ack（不重试、不进死信）                      :79-85
③ 正常                             → projectOrderFinished → ack                              :87-91
④ 抛异常                           → retry+1<=maxRetry ? publishRetry : publishToDlq → ack      :92-101
```

- 装配：`@ConditionalOnProperty(name="mall.mq.enabled", havingValue="true", matchIfMissing=true)`（`:55`）+ `@RabbitListener(queues = MqTopology.REVIEW_QUEUE)`（`:64`）⇒ **队列名就是消费者边界**。重试上限 `@Value("${mall.mq.event-max-retry:3}")`（`:61-62`），次数读自定义头 `mall-retry-count`（`MqMessages.retryCount`，缺头 = 0）。
- **`memberId == null` 的例外**（`:48-50,79-85`）：读模型 `member_id` NOT NULL 且归属校验离不开它，重投结果一样，进死信只会污染"值得人工处理"的信号。
- 成功/失败都 ack 原始消息，毒消息不会无限重入（`:44-46`）；手写 JSON 收发（`MqMessages`）而**不用全局消息转换器**（`MqMessages:21-24`：转换器是全局的、还要处理 `__TypeId__` 等细节）。

### 3.4 `mq/ReviewEventRetryPublisher`（79 行）★ "为什么消费者还要会投"

| 方法 | 投到什么 | 语义 |
|---|---|---|
| `publishRetry(event, retry)`（`:42-51`） | 交换机 `mall.oms.event` + 键 `review.retry`（重试队列） | 消息自带 TTL = `mall.mq.event-retry-delay-ms`（默认 10000，`:38-39,76-78`，`max(1,…)` 保底）；到期死信回工作队列（键 `review.redeliver`） |
| `publishToDlq(event, retry, reason)`（`:54-63`） | 键 `review.dlq` | 重试超限；带 `mall-retry-count` + `mall-fail-reason` |
| `publishRawToDlq(original, retry, reason)`（`:66-74`） | 键 `review.dlq` | 正文解析不了时**原样保留原始字节**（人工可读） |

- 作用（类注释 `:19-22`）：单体把"失败 → 投重试队列 → TTL 到期回工作队列"的**投递动作**放在发布者（生产/消费同进程）；本服务是独立消费者，这套投递必须跟着消费者走，否则失败消息无处可去。**fail-open**（`:24-25`）：连重投本身失败也只 `log.error`（消息已 ack，不会毒住队列；运维可按订单号人工补投）。
- 键名刻意独立（`review.*`，`MqTopology:76-88`）：与单体的 `event.*`、user-center 的 `notification.*` 共用会让双方死信互相串味。**重试消息正文形状不许换**（`:27-28`）：仍是 `OrderFinishedMessage` 的 JSON，换形状 = 悄悄丢掉一条待评价明细。

### 3.5 `service/impl/ReviewPendingServiceImpl`（73 行）

`projectOrderFinished(event)`（`:36-72`，`@Transactional`）：`items` 为 null/空 ⇒ `log.warn` + 返回 0（`:39-44`，`event == null` 也走这条）；逐条 upsert 累加"新增"数，日志打 `明细=N 新增=X 已存在=N-X`（`:68-70`）。
两个刻意的转换：**时间只在这里转一次**（`:46-48`，epoch millis → `MallTime.dateTimeOf(...)`，业务时区 `MallTime.ZONE`，不对齐会让 `finished_time` 整体偏 8 小时，`application.yaml:15-17` 同一口径）；`spu_title` 显式兜底空串（`:58-59`，列 NOT NULL DEFAULT ''，一个 null 会让整条事件反复重试）。
投影出一律 `commented=0`、`comment_id=null`（`:63-64`，测试断言见 `OrderFinishedMqMySqlTest:152-154`）。**幂等策略是"不判断、靠主键"**（类注释 `:19-23`）："先 SELECT 看有没有"在并发重复投递下会双写。

### 3.6 `client/MemberSnapshotApi` + `client/MemberSnapshotClient`（40 + 117 行）★ 昵称快照的唯一来源

`MemberSnapshotApi`：`@HttpExchange(url="/internal/v1/user", contentType="application/json")`（`:29`）+ `@GetExchange("/member/{id}/snapshot")`（`:38-39`），返回**下游原始响应体** `ApiResponse<MemberNicknameVO>`（不是 `T`）；这一层**不判业务码、不打日志、不降级**（`:18-24`），留给客户端类。

| `MemberSnapshotClient` 构造器 | 用途 | 关键点 |
|---|---|---|
| `(… @LoadBalanced RestClient.Builder, OutboundRestClientFactory, baseUrl, connectTimeoutMs, readTimeoutMs)`（`:65-77`） | 生产装配 | 显式 `@Autowired`（`:62-64`：两个构造器并存必须指明用哪个，否则启动即失败）；base-url 默认 `lb://mall-user-center`；`HttpServiceProxyFactory.builderFor(RestClientAdapter.create(restClient))` 生成接口代理 |

```java
String nickname = response.getData().getNickname();
return StringUtils.hasText(nickname) ? nickname : "";
} catch (Exception e) { log.warn("取会员昵称失败（不影响评价提交，快照落空串）: …"); return ""; }        // 不可达/超时/无实例/反序列化失败
```

- **失败即静默落空串，绝不抛**（类注释 `:44-48`）：昵称是展示用冗余字段，让它把一次成功的评价提交变成失败，是"把锦上添花做成单点故障"。**业务码非 0 也算失败**（`:49-50`）：user-center 用 `code != 0` / `data: null` 表达"没有这个会员"，不能当成功昵称。
- **硬超时** connect 300ms / read 1500ms（`@Value` 默认值 `:69-70`，本模块 yaml 未覆盖）——这是用户可感知的**写**路径。只声明 `id` + `nickname` 两个字段（`MemberNicknameVO:8-15`）：对方加字段不会炸，本服务也不存在"拿到会员手机号"这种能力。覆盖测试：`MemberSnapshotClientTest`（真客户端 + `http://127.0.0.1:1`）+ `CommentApiMySqlTest#submit_nicknameUnavailable`。

### 3.7 `controller/CommentController`（61 行）/ 3.8 `controller/ProductCommentController`（49 行）

端点见 §1.1。要点：类级 `@RequestMapping("/api/comment")`，路径/方法/参数名/响应类型与单体逐字一致（`:25-28`）；`@MemberId` 由 `GatewayIdentityResolver` 从网关注入头解析，**本服务不验签、不接触令牌**（`:30-33`），提交接口**不从请求体收 memberId**（`:33`）。`ProductCommentController` 单独成类是因为硬塞进 `CommentController` 就得写绝对路径的方法映射、让类级前缀名不副实（`:18-23`）；网关必须**精确匹配**这条子路径（`:31-34`：写前缀通配会把商品详情/列表一起劫走）。

### 3.9 `internal/InternalReviewController`（49 行）+ `service/impl/CommentCountServiceImpl`（64 行）

### 3.10 `config/GatewayIdentityResolver`（121 行）+ `config/WebConfig`（70 行）

身份来源：网关验签后注入 `X-Gateway-Auth`（共享密钥）+ `X-Member-Id` + `X-Member-Ver`（`GatewayAuthHeaders`）。
- 构造器（`:56-63`）读 `@Value("${mall.gateway.auth-token:}")`；**空密钥不阻止启动**，只 `log.warn`，此后需要登录的接口全部 401（fail-closed）——注释写明与单体的差别：单体能回落到"自己验签"，本服务**已经没有验签能力**。
- `resolve(request)`（`:72-78`）解析不到就抛 `BusinessException(401, "未登录")`（文案与单体逐字一致，`:51-52`）；`resolveOrNull(request)`（`:89-104`）不抛、返回 `null`。判据是 `MessageDigest.isEqual(provided.getBytes(UTF_8), expected)`（**常量时间比较**，`:94-95`）+ `parseLong(X-Member-Id)`；**不区分"没带头"与"带错头"**（`:37`，都表现为 401），且它只回答"你是谁"，不回答"登录态还作不作数"（`:40-41`）。
- `WebConfig#addInterceptors`（`:40-44`）把 `InternalApiAuthInterceptor` 挂在 `"/internal/**"`（唯一路径模式）；`addArgumentResolvers`（`:52-69`）注册匿名 `HandlerMethodArgumentResolver`，要求 `@MemberId` **且**类型是 `Long.class`（`:56-59`）——声明成 `long` 基本类型会解析不到而 500，注释拒绝"静默注入 0"（`:49-50`：那会让归属校验变成"归 0 号会员"）；解析失败由 `GlobalExceptionHandler` 转成 HTTP 200 + `code=401`（测试：`CommentApiMySqlTest#submit_andMine_requiresGatewayIdentity`）。

### 3.11 `config/InternalApiAuthInterceptor`（65 行）

`preHandle`（`:48-59`）两条分支、都是 403：`mall.internal.token` 未配置（`expectedToken.length == 0`）→ `内部接口未配置访问凭据`；头 `X-Internal-Token`（常量 `HEADER_INTERNAL_TOKEN`，`:40`）缺失或不匹配（`MessageDigest.isEqual` 常量时间比较，`:62-64`）→ `内部接口鉴权失败`。注释明确"**未配置 = 拒绝所有内部调用**（fail-closed）"（`:34`）；现状是静态共享密钥，方案 §4.10 的 HMAC + 时间戳防重放**尚未实施**（`:30-31`）。覆盖测试：`InternalReviewApiMySqlTest` 两例 403 + 一例正例。

### 3.12 `config/RabbitMqConfig`（121 行）+ `support/MqTopology`(89) + `support/MqMessages`(95)

| 角色 | 名字 | 常量 |
|---|---|---|
| 共享事件交换机（topic / durable / **非** autoDelete / 无 arguments） | `mall.oms.event` | `MqTopology.EVENT_EXCHANGE:51` |
| 业务绑定键 | `order.finished` | `EVENT_ROUTING_FINISHED:65` |
| 本服务工作队列 | `mall.review.order-finished` | `REVIEW_QUEUE:70` |
| 重试队列（无消费者，消息自带 TTL） | `mall.review.order-finished.retry` | `REVIEW_RETRY_QUEUE:72` |
| 死信队列（无消费者，仅观测/人工重投） | `mall.review.order-finished.dlq` | `REVIEW_DLQ:74` |
| 三个自有路由键 | `review.retry` / `review.redeliver` / `review.dlq` | `:84,86,88` |

- 声明参数的坑（`RabbitMqConfig:25-31`）：交换机由**多个服务各自声明**，RabbitMQ 以第一次声明为准，参数不一致直接 `PRECONDITION_FAILED` 让监听容器起不来 ⇒ 这里是 `new TopicExchange(EVENT_EXCHANGE, true, false)`（`:52-55`），与单体一字不差。**只声明自己用到的那一半**（`:19-23`）：不声明 `mall.oms.events` / `mall.user.notification`（同名队列 = 竞争消费）。

### 3.13 `support/GlobalExceptionHandler`（74 行）+ `support/RequestValidator`（90 行）

- `GlobalExceptionHandler`：`@RestControllerAdvice`，**HTTP 恒 200、业务码在 body**。`BusinessException` → 原样 code/message（`:30-33`）；`MethodArgumentNotValidException` → 400 + 首条字段提示（`:41-49`）；`HttpMessageNotReadableException` → 400 `请求体格式不正确`（`:52-56`）；`NoResourceFoundException` → 404 `资源不存在` 且不打错误日志（`:63-67`）；兜底 `Exception` → 500 `系统繁忙，请稍后重试`（`:69-73`）。**它同时是内部鉴权那道闸的出口**（`:16-18`）。
- `RequestValidator#check`（`:35-43`）把 DTO 上的 Bean Validation 跑一遍、失败抛 `BusinessException(400, 原中文提示)`；存在理由（`:17-22`）：`@Valid` 的异常只能在 Controller 层拦，**Service 层被直接调用（内部调用/测试）时完全不生效**。**报错顺序是契约的一部分**（`:24-26`）：DTO 字段声明顺序 → 同字段内"非空 → 长度 → 范围 → 格式"（`annotationRank`，`:79-89`）。

## 9. 坑与已知边界

**代码里能指到的坑（都是注释/测试记录过的）**

1. **提交的 INSERT/CAS 顺序是反的，且依赖回滚**（`CommentServiceImpl:65-69`）：不要"顺手改成先抢后写"——那样 `comment_id` 没值可写。**两个 409 分支同文案、不得合并**（`:131-133`、`:157`）：合并会让"并发抢占"这条路径失去独立观测点。
2. **`memberId == null` 的事件不进死信**（`OrderFinishedConsumer:48-50`）：重投无意义，进 DLQ 只会污染"值得人工处理"的信号。
3. **`04-backfill-pending.sql` 是历史脚本，不要重跑**（文件头 `:2-7`）：结构权威在 `V1__baseline.sql`，重跑会有两个结构来源、Flyway 校验失配。脚本另记了两个实测坑：目标列 `comment_id` 必须写全限定名，否则 `ERROR 1052: Column 'comment_id' in field list is ambiguous`（`:126-128`）；判据刻意**不**要求 `order_status = 3`（`:62-68`），因为要守的不变量与订单当前状态无关。
4. **Connector/J 默认 `useAffectedRows=false`**：`executeUpdate` 返回**匹配行数**而非改变行数，重复执行回填也返回 1885 ⇒ 幂等断言必须看"表状态摘要"（`BackfillPendingSqlTest:162-166`，踩过）。
5. **MQ 开关不要写进 `application-dev.yaml`**（`application.yaml:74-76`、`application-dev.yaml:25-26`）：profile 优先级高于 test 的 `application.properties`，写进去等于每个测试上下文都去连 broker（症状是"测试偶尔超时"）。
6. **两个令牌必须写在 `@SpringBootTest(properties=...)` 上**（`ReviewTestBase:17-26`）：写在 `src/test/resources/application.properties` 会被 dev 令牌盖掉，而"无令牌 → 403"的用例照样通过、把问题掩盖（P2/P3 各踩过一次）。**真库套件必须跨库读 `mall_trade`**，所以测试期显式把数据源覆盖回 root（`ReviewTestBase:30-39`）：运行态是最小权限账号 `mall_review`，不覆盖会有 3 个用例报 `ERROR 1142`。
7. **`@MemberId` 只支持 `Long`**（`WebConfig:49-50`）；**`@LoadBalanced` 必须标在 `@Bean` 方法上**（`LoadBalancedClientConfig:12-15`）。

**已知边界与遗留面（都能指到代码）**
