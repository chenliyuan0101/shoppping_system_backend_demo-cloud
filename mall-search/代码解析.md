# `mall-search` 代码解析

> 一句话定位：**检索域**——它维护 Elasticsearch 索引 `mall_product`（建索引、写文档、删文档、全量重建），并对外只开放 `/internal/v1/search/**` 给商品域/运维域调用；关键字检索的**降级回落 MySQL LIKE 不在这里**（它没有库，回落在 `mall-product`）。
> 范围：`src/main/java` 下 **31 个文件 / 2662 行**（口径：`Get-ChildItem -Recurse -File -Filter *.java src/main/java` 的逐文件 `\n` 计数求和，含注释与空行）；测试 **15 个文件 / 13 个测试类 / 89 例**（`src/test/surefire-reports/*.txt` 的 `Tests run` 求和）。
> 与其它文档的分工：系统布局/端口/路由见 `系统说明.md`；启动与请求生命周期见 `系统流程与三大核心功能实现.md`；**本文只讲这个服务的包怎么组织、每个类怎么实现、改代码要注意什么**。

## 2. 分层与包职责

- `internal/`：只放入站端点，**不放业务逻辑**——每个方法都是"解包请求 → 调 `ProductSearchService` → 套 `ApiResponse`"，最多一次参数归一化（`request.normalizedPageNum()/normalizedPageSize()`）。
- `service/` + `service/impl/`：能力接口（含 `INDEX` 常量）+ 唯一实现。接口 javadoc 承担**契约文档**职责（尤其 `markDirty` 与 `markPending` 的分工、`getIndexedDoc` 与 `findById` 的失败口径差别），改代码前必读；实现是**唯一持有 `ElasticsearchClient` 的地方**，别把 ES 调用漏到 `internal/` 或 `client/`。
- `client/`：出站。规则来自 ArchUnit 白名单（`CodeStyleTest.java:81-91`）：只允许 `*Api`（声明式接口）/ `*Client`（域语义）/ `*Factory` / `*Interceptor` / `*Exception`。`Api` 只管"HTTP ↔ 类型"，`Client` 管连接装配、错误语义、形状适配（`ProductIndexDocApi.java:28-34`）。
- `config/`：装配（白名单 `CodeStyleTest.java:126-140`）。**组装根就在这个包**：`SearchApplication`（`@SpringBootApplication` + `@EnableScheduling`）扫 `com.mall.search.**`；MQ 拓扑声明在 `RabbitMqConfig` 而不在共享内核——`MqTopology.java:6-10` 解释了原因（常量会被 javac 内联，业务域"看起来"不依赖组装根）。
- `mq/` / `task/` / `dto/` / `support/`：四类各自的白名单分别在 `CodeStyleTest.java:152-163`（`*Consumer|*Publisher|*Message|…`）、`:143-149`（只放 `*Task`）、`:58-77`（`VO|Request|…|Doc|…`，这也是 `ProductSearchDoc` 必须叫 `Doc` 的原因）、`:176-183`（noClasses 规则：**support 不得依赖 internal/service/client**）。契约面（`ApiResponse`/`BusinessException`/`GlobalExceptionHandler`）是**本服务自持副本**，与其它服务逐字同构，不走共享 jar（`CodeStyleTest.java:20-21`）。
- 架构闸门**没有 B5/B6 这类编号**：本模块的可执行规范就是 `architecture/CodeStyleTest` 的 10 条（命名后缀 + 包职责），grep 不到 `B5`/`B6`/`ModuleBoundary`。

## 3. 核心类详解

### 3.1 `internal/SearchInternalController`（157 行）

一句话：本服务**唯一**的入站面，8 个端点的薄壳。

- `status()`（`:77-90`）→ 拼一个 `SearchStatusVO`：索引名恒取 `ProductSearchService.INDEX`、`count()`、`pendingCount()`、`titleAnalyzer()` **四个各自独立调用**，再加 `esClusterInfo()` 的 5 个字段。
  - **不变量**：自检接口在 ES 挂掉时**仍然返回 HTTP 200/code=0**，用 `docCount=-1` 表达"不可用"（`SearchDegradedEsTest#status_esDown_reportsDocCountMinusOne`）。
- `reindex()`（`:64-67`）→ 直接透传 `productSearchService.reindex()`；失败由实现抛 `BusinessException(500, …)`，**不会**返回 `ReindexResult`（哪怕 `indexed=0`）。
- `markDirty(...)`（`:134-138`）→ 请求体 `@RequestBody(required = false)`：**无 body / null / 空列表都是 `added:0` + `code=0`**，不是 400（`InternalSearchApiEsTest` 的 "[内部接口/mark-dirty] 空/null/无 body ⇒ added:0"）。
- `product(spuId)`（`:153-156`）→ 返回索引文档；**文档不存在 ⇒ `code=0` + `data:null`**；**ES 读不到 ⇒ `code=500`**（这是本类最容易写反的一处，见 §3.3 的 `getIndexedDoc`）。
- ⚠️ **本服务不自己查 MySQL 做降级**（`:33-36`）：「ES 挂了 → 回落 MySQL LIKE」这条降级属于 `product`（它才有库）。

### 3.2 `service/ProductSearchService`（160 行）

一句话：能力接口 + **索引名契约**。

- `String INDEX = "mall_product";`（`:21`）——**不改名、不加别名**。`InternalSearchApiEsTest` 有专门用例钉"恒为 `mall_product`，且没有别名"。
- 接口 javadoc 写死了两处**必须区分**的语义（改代码前先读）：
  - `markDirty`（`:127`）＝**发布方**语义：MQ 主通道，失败才回落 Redis；
  - `markPending`（`:92`）＝**兜底通道**语义：只写 Redis 集合，收敛延迟 = 定时任务周期（默认 15s），且**刻意不投 MQ**（`:85-87`：两边都投会让同一个 spuId 被消费两遍）。
  - `getIndexedDoc`（`:114`）vs `findById`（`:156`）：同一份 ES `get`，但**失败口径不同**——前者 ES 不可达抛异常，后者吞掉返回 null。

### 3.3 `service/impl/ProductSearchServiceImpl`（788 行，本文主体）

一句话：索引的一切读写都在这；内容来自 `ProductIndexDocClient`，ES/Redis 之外不碰任何存储。

**常量与字段**：`REINDEX_PAGE_SIZE = 500`（`:95`，重建每页拉多少条）、`REINDEX_MAX_PAGES = 1000`（`:98`，分页防呆）、`BULK_BATCH_SIZE = 500`（`:101`，bulk 写/删批大小）、`configuredTitleAnalyzer`（`:115`，`${mall.search.title-analyzer:auto}`）、`resolvedTitleAnalyzer`/`indexEnsured`（`:119`/`:127`，进程内 `volatile` 缓存，后者只在 `reindex()`/`ensureIndex()` 置位）。

**`reindex()`（`:129-176`）——四步，顺序即语义**：① `fetchAllDocs(docs)` 向 product **逐页取齐内容**（`:136-143`，失败 ⇒ `BusinessException(500,"商品索引重建失败：…")`，**此时索引还没被碰过**）→ ② `recreateIndex()` 删旧索引、建新索引（显式映射，`:148`）→ ③ 按 `BULK_BATCH_SIZE` 分块 bulk（`:155-163`，errors 只记前 3 条 warn）→ ④ `indices().refresh(INDEX)` 整批**恰好一次**刷新（`:166`）。

- **不变量**：**取数全部拉完再动索引**（`:134-135` 注释原文："product 不可达时必须'索引保持原样'，而不是'删了旧索引、新文档没写进去'"）。守它的用例：`ProductIndexContentStubbedEsTest` "[失败语义/reindex 取数失败]…索引里原有文档一篇不动 —— 绝不写半截索引"。
- **返回值**：`ReindexResult(INDEX, resolvedTitleAnalyzer, indexed, onShelfTotal, took)`（`support/dto/ReindexResult.java:12`）；`indexed` 只统计 `item.error()==null` 的条目（`:162`），所以 `indexed != onShelfTotal` 就是"有写入失败"。
- ⚠️ 重建期间该索引**真的不存在**（删旧 → 建新，不是别名切换）——`SearchTestBase.java:70-75` 记录了实测撞上的 `no_shard_available_action_exception`，并因此给了 10s 有界等待。

**`fetchAllDocs(sink)`（`:590-615`）——"取不满必须炸"**

```java
for (long page = 1; page <= REINDEX_MAX_PAGES; page++) {
    IndexDocsResult result = productIndexDocClient.page(page, REINDEX_PAGE_SIZE);
    onShelfTotal = result.totalInShelf();
    sink.addAll(result.docs());
    if (result.size() < REINDEX_PAGE_SIZE) break;   // 页不满即停：不按 total 死算页数
}
if (sink.size() < onShelfTotal) {
    throw new BusinessException(500, "文档取不满（" + sink.size() + "/" + onShelfTotal + "）");  // :612
}
```

- **为什么"页不满即停"不等于"取齐了"**（`:582-588` 注释）：product 报在架 1000、实际只给 800（下游分页 bug / 期间数据变动 / 触到页数上限），原来会**静默继续**，然后删旧索引、写进一份只有 800 篇的新索引——"索引少了 200 篇商品"而**全程没有报错**。
- **文案契约**：这里**不带**"商品索引重建失败："前缀（`:609-611`），因为 `reindex()` 的 catch 已经加了；最终对外文案 = `商品索引重建失败：文档取不满（2/5）`。用例：`ProductIndexContentStubbedEsTest` 的 "[失败语义/取不满] … reindex 报 500「文档取不满」，且索引一篇不动"。

**`bulkWriteBatch(allIds, docs, idsToDelete)`（`:347-379`）——写放大收口的核心**

```java
ops.addAll(indexOps(docs));                                   // _id = spuId ⇒ 覆盖写天然幂等
for (Long spuId : idsToDelete) ops.add(delete…);
… 分块 bulk（每 BULK_BATCH_SIZE 一批）…
for (BulkResponseItem item : response.items())
    if (item.error() != null) failed.add(parseSpuId(item.id()));   // 只有报错的 id 算失败
elasticsearchClient.indices().refresh(r -> r.index(INDEX));         // :372 整批唯一一次刷新
```

四条纪律写在同一段 javadoc 里（`:327-337`）：① **不许在循环里 refresh**（逐篇 `refresh(WaitFor)` 就是写放大成因，45 篇实测 60,906 ms）；② **返回前必须 refresh 一次**（否则"调用返回 = 已可检索"这条承诺没了，表现是"同步成功了但搜不到"，而调用方拿到 `true`）；③ **只刷 `INDEX` 这一次**，不刷整个集群；④ **失败按 per-item 结果映射回 id**，`result=not_found`（删一个不存在的文档）**不算失败**（与单篇 `deleteProduct` 的幂等吞掉口径一致）。
**异常口径**（`:339-341`、`:373-377`）：bulk 或 refresh 抛异常 ⇒ **这批全部算失败**——写入可能已生效，但"不保证可见/不保证写全"，按失败重试是幂等的；反过来报成功则可能**永久丢一篇**。
`syncProducts` 与 `syncByBrand` **共用这一份实现**（`:304-305` 注释：避免两条路径各自漂移）。

**`syncProduct(spuId)`（`:204-222`）——单篇，保留 `refresh(WaitFor)`**

- 取数改向 product：`bySpuIds(List.of(spuId))`；**返回里没有该 id ⇒ 下架/删除/不存在 ⇒ `deleteProduct(spuId)` 并返回 `true`**（下架也算同步成功）。写入走 `indexDoc`（`:404-418`），带 `.refresh(Refresh.WaitFor)`（`:412`）。
- **为什么单篇刻意不加改动**（类注释 `:82-87`）：`POST /sync/{spuId}` 的对外承诺是"**返回即已按最新状态落索引并可检索**"，去掉那次刷新会把它变成"最多 1s 后可见"；bulk 对单篇没有收益。**这是有意的，不是漏改**。失败**只告警返回 false，不抛**（`:217-221`）：索引同步失败不该阻塞商品写操作。

**`syncProducts(spuIds)`（`:224-277`）——批量唯一入口**

① 空集合 ⇒ `List.of()`，**一次 ES 都不碰**（`:228-230`）；② 入参**保序、保留重复与 null**（`:229-232`、`:267-273`：失败列表必须能逐条映射回原输入，否则"消费侧 failed → 重试队列 → DLQ"那条链的条数与内容会漂）；③ 一次 `bySpuIds(ids)` 取齐内容（`:244`，**不再逐条回拉**——N+1 的坑踩过），差集 = 要删的 id（`:253`）；④ 一次 `bulkWriteBatch`（`:257`）；取内容阶段就失败 ⇒ **整批按失败**且索引一篇不动（`:258-265`）。

**`syncByBrand(brandId)`（`:288-320`）**：`byBrand(brandId)` 一次取齐 → `bulkWriteBatch(ids, docs, List.of())` → 返回 `docs.size() - failed.size()`（"成功写入 ES 的条数"，ES 不可达时是 0）。
- ⚠️ 类注释 `:291-295` 记了一次**自己引入的缺陷**：第一版对每个 doc 调 `syncProduct`（它会**再向 product 拉一次**）⇒ 品牌 937（45 个在架商品）变成 45 次 HTTP 往返，live 实测 59,993ms，`-m 20` 的调用被超时切断、表现成"返回空 data"。修法：内容已一次取齐，直接写索引。
- ⚠️ 注释 `:298-301` 记了改前活体基线：逐篇 `refresh(WaitFor)` = **60,906 ms**（≈1.35s/篇）。判据用例：`ProductIndexBatchWriteEsTest` 的 "[批量/耗时] 45 篇…" 与 "[批量/写放大] 整批 1 次 bulk + **恰好 1 次** refresh"。

**检索：`search(...)`（`:178-202`）/ `buildQuery`（`:663-685`）/ `buildSort`（`:688-696`）**

- 只返回**命中的 spuId + 总数**（`ProductIdPage`），展示字段由调用方回自己的库装配（`dto/ProductIdPage.java:8-9`）；`trackTotalHits(enabled(true))`（`:187`）保证 `total` 是真值，`hits.total()==null` 时退化成命中数（`:196`）。
- 查询 DSL 与原 MySQL 货架 SQL 对齐（`:652-661`）：关键字 `match_phrase` on `title`（逼近 `LIKE '%kw%'`）、类目 `terms`（**"含子类"的展开由调用方 `CategoryScopeResolver` 做**）、品牌 `term`、价格 `range` on `minPrice`（闭区间）、外加 `status=1` 双保险（用 `EnableStatus.ENABLED` 常量，`:682`）。排序四种 + **一律用 `spuId ASC` 兜底**保证分页稳定（`:687`），`sort` 为 null 时按 `default`＝`sales` 降序（`:689-694`）。
- ES 异常 ⇒ `throw new IllegalStateException("Elasticsearch 检索失败: …")`（`:200`），**给调用方决定降级**（"这里只补充上下文后抛出"）。

### 3.7 `mq/ProductSyncPublisher`（214 行）——投递端

- 三种路径（`:22-29`）：`publishSpuIds`（正常）、`publishRetry`（TTL 延迟重投）、`publishRawRetry/publishRawToDlq`（正文解析不了时原样重投/进死信）。投递按 `ProductSyncMessage.MAX_BATCH = 100`（`ProductSyncMessage.java:22`）分批。
- **`publishSpuIds(ids, onFailure)`（`:73-90`）＝业务链路推荐入口**，核心是 **`afterCommitOrNow`（`:174-185`）**：在事务里就注册 `TransactionSynchronization.afterCommit`，不在事务里立刻执行。**为什么必须等提交后**（`:66-69`）：订单/退款链路是在**事务内**调 `markDirty` 的，消息若立刻发出去，消费者可能先于事务提交去读库（读不到刚扣的库存），把**旧值**写进索引——"索引里的库存比真实库存多"且**不报任何错**；**兜底动作也要等提交**（`:76-78`）：兜底之一是"直接同步写 ES"，放在事务内会让 ES 的 2s/5s 超时压住行锁，还会产生"库里没提交、索引已可见"的脏文档。
- 失败**一律 fail-open**（记 warn 不抛，`sendFresh` `:161-171`；兜底动作本身也包在 `runQuietly` `:188-197`）。`mqEnabled` = `${mall.mq.enabled:true}`（`:41`）；`retryDelayMs` = `${mall.mq.sync-retry-delay-ms:10000}`（`:44`），写进**每条消息自己的 TTL**（`MqMessages.json(payload, ttl, …)`）。

### 3.8 `task/ProductSearchSyncTask`（57 行）——Redis 兜底 drain

```java

@Scheduled(fixedDelayString = "${mall.search.sync-interval-ms:15000}", initialDelay = 20_000) // :42
```

## 9. 坑与已知边界

只写代码里能指到的：

1. **`ensureIndex()` / `indexEnsured` 是死代码，且注释明说了**（`ProductSearchServiceImpl.java:734-737`）：单体里这个方法就没有调用点，本服务逐字保留而不是顺手删——去掉死代码属于行为变更。`syncProduct` 前的自检因此**并不存在**（ES 会为不存在的索引自动创建 + **动态映射**，映射就错了）；`recreateIndex` 的并发兜底（`:713-724`）就是为这个场景写的。
2. **重建窗口内该索引真的不存在**：`reindex()` 是"删旧 → 建新"而不是别名切换，所以重建期间检索会报错，且**共享该索引的其它进程/用例**会看到 `no_shard_available_action_exception`。`SearchTestBase.java:70-75` 记录了实测撞上并给出 10s 有界等待的处理。
3. **`drainPending` 对成员值不做形状校验**：`ProductSearchServiceImpl.java:456` 是 `members.stream().map(Long::valueOf).toList()`，没有 try/catch。这把 key 是**跨服务共享**的（§4），一旦有人写进非数字成员，定时任务会抛 `NumberFormatException` 并整轮中断（`ProductSearchSyncTask` 里没有 try/catch）。（推测：正常写入方都写 `String.valueOf(spuId)`，所以当前不会触发；依据是 `:434`、`:493` 与 product 侧 `SearchUnavailableProductSearchService.java:286` 的写法。）
4. **`ProductSearchSyncTask` 的"失败回队"走的是 `markDirty`，即发布方语义**：MQ 可用时失败的 id 会被**再投一次 MQ**，而不是只 `SADD` 回 Redis 集合（`:53` + `:433`）。若有人按"回队 = 回到 Redis"去理解，会误判收敛路径。
5. **同一份 ES `get` 有两种失败口径**（`getIndexedDoc` 抛 / `findById` 吞），且它们名字都很自然——合并两者会立刻破坏 §8 里那条不变量。接口 javadoc（`ProductSearchService.java:106-113`）专门写了"别合并两者"。
6. **`markDirty` 与 `markPending` 不能互相替代，且 `mark-dirty` 端点目前没有生产调用方**（`ProductSearchService.java:79-87`）：前者是 MQ 主通道（亚秒级），后者只写 Redis（延迟 = 15s 周期），在 `markPending` 里顺手投 MQ 会让同一个 spuId 被消费两遍（幂等，但白干一遍活）。而 grep 下来 `POST /internal/v1/search/mark-dirty` **只有测试在调**：`mall-product` 的降级实现是自己直接 `cacheService.setAdd(CacheKeys.esPendingSync(), …)`（`SearchUnavailableProductSearchService.java:287`），`mall-trade` 持有同名 `CacheKeys.esPendingSync()`（`mall-trade/.../common/CacheKeys.java:86`）但没有调用方——端点存在（P6-5 #5 "补空洞"），接线尚未落地。
7. **`fetchAllDocs` 的"页数上限"告警只在 `page == REINDEX_MAX_PAGES` 且该页满时触发**（`:599-602`），达到上限后循环自然退出、不会抛异常；真正兜住"取不满"的是 `:608-613` 的比对（`sink.size() < onShelfTotal`）。若 product 报的 `totalInShelf` 本身偏小（等于少给的那部分），这道闸门**不会**触发——那时只能靠 §4 的逐字段审计发现（推测：脚本 ① 用脚本自己查库统计的在架数作为真值，能反向暴露这种情形；依据 `p6-index-content-audit.ps1:31-36`）。
8. **`reindex()` 期间没有任何互斥**：两个并发 `reindex` 会互相删索引重建（`recreateIndex` 的兜底只保证"最终存在的是带正确映射的索引"，不保证内容完整）。代码里没有锁、也没有分布式互斥。
9. **两处"刻意的不同"别当成不一致**：① `ProductIndexDocClient` 的错误日志是 ERROR 级并带请求体（`:131`、`:135`），而 `mall-admin` 的看板客户端刻意只记 debug（`:41-42` 注释）——本类的失败是"明确的失败"，不是预期内的降级；② 测试期默认关 MQ（`src/test/resources/application.properties:8-14`）是刻意的，开着的话本服务的消费者会与"单体里还在跑的那个消费者"抢同一条工作队列里的真实消息，MQ 专项套件用**用例级** `properties` 显式打开。
